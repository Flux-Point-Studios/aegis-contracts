## Findings considered but rejected (with reason)

### CBOR canonical-form drift (Attack surface 1)
**Considered.** Looked for any code path where Python re-serialises Plutus Data after `_recompute_script_data_hash` computed the body hash.
**Rejected.** `tx_build.py:794` calls `tx.to_cbor_hex()` once; wallet signs over the body byte-range verbatim. `sign_and_submit.ts:300` copies the body bytes via `slice()` — no codec touched. `tx_submit.py:283` uses `submit_tx_cbor(tx_bytes)` (raw-bytes), explicitly avoiding PyCardano's round-tripping `submit_tx(parsed_tx)` per `:275-282`. The only CBOR re-encode in the merge path is the vkey-witnesses dedup branch (`sign_and_submit.ts:263-278`), and it only fires when `merged.get(0)` is non-empty — never the case for server-built unsigned txs (PyCardano emits `vkey_witnesses = None`; wallet bytes are spliced verbatim at `:284`).

### Datum schema confusion / versioning (Attack surface 2)
**Considered.** V11 = 11 fields, V12 = 13 fields. Tried to construct a CBOR blob that decodes as both shapes.
**Rejected.** Aiken's `expect pdat: PolicyDatum = raw_pdat` requires the outer Constr's payload to have **exactly 13** elements; an 11-element list fails the `expect`. The same applies on the Python side at `policies.py:1234` — `len(fields) != 13` returns `None`. The constructor index (Constr_0) is shared, but the payload arity differentiates. No CBOR ambiguity gives both decoders the same wire form. V11 stranded UTxOs at the V11 validator hash are inert: V12.2 validator code doesn't see them; V11 validator still decodes them; no cross-binding via this vector.

### Redeemer ambiguity (Attack surface 3)
**Considered.** `PolicyRedeemer { Claim, BatchClaim, Expire, BatchExpire, Cancel }` use Constr_0..4. `PoolRedeemer { Underwrite, ProcessClaim, AddLiquidity, RemoveLiquidity, BatchUnderwrite, BatchExpireProcess, AcceptCancellation }` use Constr_0..6. Tried to construct CBOR that decodes as two different variants.
**Rejected.** Aiken's positional Constr encoding is bijective on (constr_id, payload). The redeemers with payloads (`Underwrite { coverage, premium }`, `ProcessClaim { payout }`, etc.) have distinct constr_ids AND payload arities. The empty-payload redeemers (Claim/BatchClaim/Expire/BatchExpire/Cancel) all have distinct constr_ids. Off-chain Python's `_REDEEMER_TAG_MAP` in `tx_build.py:489-504` is purely a display surface; the on-chain decoder uses the constr_id directly. There's no CBOR shape that's two valid redeemers at once.

### Witness set forgery / double-witness (Attack surface 4)
**Considered.** v8 relay-presigned-auth has the `auth_commitment: Option<ByteArray>` field — checked whether a vkey witness signed for one tx body could be lifted into a different body.
**Rejected.** Ed25519-Cardano signs over `blake2b256(body_bytes)`. Two distinct txs trivially produce different `body_bytes`, hence different hashes, hence the same Ed25519 signature does NOT validate over both. The relay-presigned-auth `auth_commitment` is a 32-byte BLAKE2b-256 hash binding the auth witness to one specific policy datum (coverage + premium + start + expiry + insured + provider + nft). Witness-cross-tx lift is structurally impossible.

### Oracle signature path (Attack surface 5)
**Considered.** `publisher/publisher/tx_builder.py:158-163` signs the publish tx with the publisher mnemonic via `builder.build_and_sign`. Submit via `context.submit_tx(signed.to_cbor())`. The price datum is `RawPlutusData(cbor2.loads(datum_blob))` — not signed separately.
**Rejected.** The publish tx is just a regular Cardano tx: the publisher's vkey signature covers the body, which references the OUTPUT carrying the inline price datum. The chain's tx-id binding means the datum can't be lifted to another publisher-address output without re-signing. The consumer (Aegis policy validator at Claim/Cancel) consumes the publisher UTxO as a reference_input; the validator pins (a) NFT membership in `aegis_self_canonical_nfts`, (b) `payment_credential == VerificationKey(aegis_self_publisher_vkh)` (compile-time pinned in `types.ak:478`). For an attacker to publish a forged price: they must control the publisher key OR mint under the one-shot NFT policy (already consumed at mint time per `oracle/aegis_self.ak:17-20`). Replay-after-correction is closed by L-003's `tx_lower >= price.observed_at` (`policy.ak:199,260,378`).

### BLAKE2b commit (Attack surface 6)
**Considered.** Three BLAKE2b sites: (a) `derive_policy_id` BLAKE2b-224 over an 80-or-82-byte preimage (`policies.py:1147-1169`), (b) `tx_id_partial` SHA-256 over body CBOR (`tx_build.py:802`), (c) the auth_commitment BLAKE2b-256 in `offchain/.../tx_builder_auth.py`.
**Rejected.** (a) BLAKE2b is not length-extendable. The preimage uses fixed-width fields (28 + 8 + 8 + 8 + 8 + 28 + 32 + 2 = 122 bytes for single; +2 for batch = 124 bytes for batch). Single vs batch preimage byte-counts differ structurally (122 vs 124) AND the `batch_index` salt is appended; collision between single and batch policy_ids is infeasible. (b) `tx_id_partial` is SHA-256 and is informational only — surfaced in the build payload for client-side UX checking; the chain identifies the tx by BLAKE2b-256 over body bytes (computed at `tx_submit.py:110`). No security-sensitive code consumes `tx_id_partial`. (c) auth_commitment is 32 bytes (enforced at `policies.py:868`), used as an opaque label against tampering — the validator checks bytewise equality (no truncation).

### Plutus Data round-trip (Attack surface 7)
**Considered.** Tried to construct a `PolicyDatum` with edge values (negative ints, large bytestrings, deeply-nested `Option<Address>`) and re-decoded through both Python (`_try_parse_policy_datum`) and Aiken (`expect pdat: PolicyDatum`).
**Rejected.** PyCardano's PlutusData encoder uses the Plutus Constr_0 indefinite-length form (`d8 79 9f ... ff`) — pinned at `reference_aegis_v8_cbor_canonical.md`. Aiken's decoder is shape-tolerant on definite-vs-indefinite as long as the Constr tag + arity match. Negative ints: `strike_price: Int` and `coverage_amount: Int` are Aiken `Int` which is CBOR signed-integer-or-bigint (`majortype 0 or 1`); the Aiken validator's `expect` doesn't care about sign, but downstream checks (`coverage > 0` at `pool.ak:619`) reject negatives. Large bytestrings: `oracle_nft: ByteArray` has no explicit length check in the type, but `is_canonical_oracle_nft` requires membership in a 28-byte allowlist, so a non-28-byte value never matches. Nested `Option<Address>` with `Pointer`-form stake credential: the off-chain `_PlutusPointer` class (`policies.py:632-643`) round-trips correctly, but Aegis never emits Pointer stakes (per `policies.py:801`); a partner-supplied Pointer-stake address would be rejected at off-chain decode time before reaching the validator.

### Ed25519 verification edge cases (Attack surface 8)
**Considered.** Grep for `verify_ed25519_signature` / `verify_ecdsa` / `verify_schnorr` in `contracts/`.
**Rejected.** Zero hits. The Aegis validators do not perform custom signature verification — all signature checks are delegated to the Cardano ledger's vkey witness layer, which uses Cardano's ZIP-215-adjacent Ed25519 semantics. The only authorisation primitive in the validators is `must_be_signed_by(extra_signatories, vkh)` at `policy.ak:348` (Cancel branch), which checks list membership of the insured's vkh in `extra_signatories` — that's a structural check against the body's `required_signers` field, not a signature verification. Cofactor / small-subgroup attacks against Ed25519 are out of scope for application validators; they would be ledger bugs.

### Script address vs script hash checks (Attack surface 9)
**Considered.** Reviewed all 17 `payment_credential` references in `contracts/`. The pattern is consistently `Script(h) -> h == expected_hash` (hash equality) rather than `Address(...) == expected_address` (full address equality).
**Rejected.** Hash-equality is the correct check — stake-credential differences must not break the validator's ability to recognize a canonical script. The exceptions where full `Address` equality IS used are intentional: `pool.ak:574` (`output.address == own_address` for the pool continuation, where the pool's stake delegation is fixed at deploy time and must NOT be substituted) and `pool.ak:518` (`o.address == addr` for team/partner outputs, where the operator-pinned team_address includes the stake part). Cross-validator composition (Indigo): `oracle/indigo.ak:200-203` pins by hash via `resolve_paired_script_hash` indexed lookup, and the canonical NFT is the cross-binding key — no ambiguity.

### Cost-model attacks (Attack surface 10)
**Considered.** Tried to construct a tx where script execution units approach the per-tx limit, such that a concurrent benign tx with overlapping inputs is bumped.
**Rejected.** The Aegis validators have empirically-measured ex_units around ~7M mem / ~2.5B steps per Claim (per smoke runs documented in `redteam/V12.2_ROUND_7_REPORT.md` lines 56). Conway protocol limits are 140M mem / 10B steps per tx. There's no path where Aegis exhausts a Conway tx's budget. Concurrent-tx bumping happens at the mempool layer (cardano-node), not at the Aegis validator layer — and is bounded by input-conflict, not budget overlap. No validator-side change can create this attack window.

## Confidence level

**High confidence: zero new cryptographic-class findings.**

The cryptographic primitives (Ed25519, BLAKE2b-224/256, SHA-256), the CBOR canonicalisation invariants (Constr_0 indefinite-length form, no codec round-trip on witness merge, deterministic cost-model encoding), and the schema/redeemer constr-id alignment are mainnet-ready. The two non-cryptographic carryovers from R7 (R7-A min-premium economic DoS, R7-B Indigo BatchClaim availability) are unchanged — R7-B has a one-line fix queued for v12.3; R7-A is an operator policy decision.

Confidence is calibrated against the negative-result rule: I actively tried to construct (a) a CBOR ambiguity, (b) a redeemer ambiguity, (c) a witness-lift, (d) a schema-confusion preimage, (e) a script-hash-vs-address substitution, and could not.

**Recommended next-round focus:** off-chain economic-DoS shapes beyond R7-A, plus end-to-end fuzzing of build → sign → submit → Plutus-rollback on preprod.
