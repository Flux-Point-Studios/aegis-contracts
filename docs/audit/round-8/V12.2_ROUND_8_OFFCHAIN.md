## NEW findings (Round 8)

### Finding R8-OFFCHAIN-1 — Indigo provider missing from oracle dispatcher (HIGH availability)

- **Severity:** HIGH (availability). Not a drain primitive. Bricks every Indigo-bound claim/cancel/batch-claim through the user-facing build endpoints.
- **File:Line:** `D:/aegis/api/oracles/dispatcher.py:207-272`
- **Description:**
  `parse_provider_label` (dispatcher.py:69-104) accepts `"indigo"` and returns `PROVIDER_INDIGO = "indigo"`. The package re-exports `PROVIDER_INDIGO` (oracles/__init__.py:51). The V12.2 NEW resolver `oracles.indigo.resolve_indigo_oracle` (oracles/indigo.py) exists and works (read endpoint `/api/oracle/indigo/price` proves this — server.py:1766-1840).
  But `resolve_oracle(context, provider, ...)` has only three branches: `PROVIDER_CHARLI3` (line 209), `PROVIDER_ORCFAX` (line 220), `PROVIDER_AEGIS_SELF` (line 242). The Indigo case falls through to `raise ValueError(f"Unhandled oracle provider: {canonical!r}")` at line 272.
  Downstream the claim/cancel/batch-claim builders all call `resolve_oracle(..., provider=cancel_provider_label, ...)`:
  - `policies.py:2709` — single Claim preflight
  - `policies.py:3062, 5035` — Batch Claim
  - `policies.py:3573` — single Cancel preflight
  - `policies.py:4223, 4389` — claim_policy/build_claim_policy_tx paths
  Each one wraps the `ValueError` as `f"Oracle ({provider_label}) unavailable for cancel: {exc}"` — so the API returns a 400 with `"Oracle (indigo) unavailable: Unhandled oracle provider: 'indigo'"` for every Indigo policy.

  **The R7 report's claim that "single-policy Indigo Claim still works" is wrong on the off-chain side.** The on-chain validator accepts it; the off-chain build endpoint refuses to construct the tx. An Indigo-bound policy is unrescuable through the API today.

- **Exploit construction:**
  1. User underwrites with `oracle_provider="indigo"` and `asset="IUSD"` against the V12.2 R7 pool via `POST /api/policies/create/build` (this succeeds — Underwrite doesn't go through `resolve_oracle`; it only embeds the NFT bytes via `_resolve_oracle_nft_bytes`).
  2. iUSD depegs. User POSTs to `/api/policies/{utxo}/claim/build`:
     ```
     curl -X POST https://api-v3.fluxpointstudios.com/api/policies/<tx>%23<idx>/claim/build \
       -H 'Content-Type: application/json' \
       -d '{"user_address":"addr_test1..."}'
     ```
  3. Response: `400 {"detail":"Oracle (indigo) unavailable for claim: Unhandled oracle provider: 'indigo'"}`.
  4. The user's only recovery path is a direct cardano-cli claim against the live validator — which the operator must build for them out-of-band. The audit handoff doesn't document this.

- **Chain effect:**
  None — no value is at risk on chain. The on-chain validator (post R7-B) accepts both single and batch Indigo claims. The pool can pay out via a hand-built tx. But every user flow that touches the API hits a hard 400.

- **Remediation suggestion:**
  Add the Indigo arm in `oracles/dispatcher.py:268` (mirror the AegisSelf shape — single UTxO reference input):
  ```python
  if canonical == PROVIDER_INDIGO:
      from . import indigo as _indigo
      # Reverse-lookup the iAsset symbol from oracle_nft if not provided
      resolved_asset = asset
      if resolved_asset is None and oracle_nft is not None:
          # 4 V12.2 iAsset NFTs — look up by bytes match
          nft_bytes = bytes(oracle_nft)
          for iasset in _indigo.SUPPORTED_IASSETS:
              candidate = _indigo._nft_for_asset_and_network(iasset)
              if candidate and bytes.fromhex(candidate) == nft_bytes:
                  resolved_asset = iasset
                  break
      utxo, parsed = _indigo.resolve_indigo_oracle(
          context=context, asset=resolved_asset,
      )
      return OracleResolution(
          provider=PROVIDER_INDIGO,
          reference_inputs=[utxo],
          parsed=parsed,
      )
  ```
  Add regression tests in `tests/test_oracle_dispatcher.py` covering each of the 4 iAssets, and a negative test that asserts an Indigo policy's claim/cancel preflight succeeds against a mocked resolver.

### Finding R8-OFFCHAIN-2 — Rate limiting wired but never decorated on routes (MEDIUM DoS)

- **Severity:** MEDIUM (denial of service; non-drain).
- **File:Line:** `D:/aegis/api/server.py:312-361` (limiter setup) + every `/build/*` and `/api/tx/submit` route (lines 1293-3933).
- **Description:**
  Module banner at `server.py:312-327` documents three env-controlled limits:
  ```
  AEGIS_RATE_LIMIT_BUILD   default "60/minute"
  AEGIS_RATE_LIMIT_SUBMIT  default "30/minute"
  AEGIS_RATE_LIMIT_READ    default "300/minute"
  ```
  `Limiter(...)` is constructed with `default_limits=[RATE_LIMIT_READ]` (server.py:336), and the docstring at line 325 says "Per-route enforcement uses the @limiter.limit decorator on the relevant endpoint definitions."
  **No endpoint has a `@limiter.limit(...)` decorator anywhere in the codebase.** Grep:
  ```
  grep -rn "@limiter\." /d/aegis/api/  →  only the comment lines 325 + 350
  ```
  Net effect: every endpoint — including the expensive `/build/*` paths that hit Blockfrost + recompute `script_data_hash` + run the full `TransactionBuilder` — is governed by `RATE_LIMIT_READ` (300/min), not `RATE_LIMIT_BUILD` (60/min) or `RATE_LIMIT_SUBMIT` (30/min). An attacker can sustain 300 builds-per-minute per IP. Each `/build` call burns one Blockfrost query for protocol params + one for UTxOs at the user_address + one for the pool UTxO + (post Wave 4) one for the Indigo feed. Multiplied across endpoints, a coordinated 5-IP burst comfortably exhausts the Blockfrost free-tier quota for the day.

- **Exploit construction:**
  ```
  while true; do
    curl -s -X POST https://api-v3.fluxpointstudios.com/api/policies/create/build \
      -H 'Content-Type: application/json' \
      -d '{"user_address":"addr_test1qrhy5kgmerdzeefg2e3ujz3sht5wsce5w82jyme4k6n0t99zx9jlzjdkarq5v5n68e37hss6jgyuyutjn6dstg4evgwqfnsjd5","strike_price":0.30,"coverage_ada":5,"duration_days":1,"oracle_provider":"aegis_self"}'
  done &
  # spawn 5 of these from rotating IPs.
  ```
  Each call is ~1.5 seconds of API work + 4 Blockfrost queries. At 300 builds/min × 5 IPs = 1500/min ≈ 6000 Blockfrost calls/min. Free tier (Blockfrost) is 100k/day. Burns the daily quota in ~17 minutes. API still answers 200s until that point; once Blockfrost 429s, every read endpoint returns 503 too.

- **Chain effect:**
  None directly, but the build endpoints become unavailable to legitimate users during the burn window.

- **Remediation suggestion:**
  Decorate every `/build/*` endpoint with `@limiter.limit(RATE_LIMIT_BUILD)` and the `/api/tx/submit` endpoint with `@limiter.limit(RATE_LIMIT_SUBMIT)`. The simplest patch is a sweep across server.py:1346-3933 to add `@limiter.limit(RATE_LIMIT_BUILD)` above every `async def build_*_endpoint(...)`. Add a `tests/test_rate_limit.py` that POSTs 70 requests in a minute from a single IP and asserts the 61st returns 429.

  Alternative: tighten `default_limits=[RATE_LIMIT_BUILD]` in `Limiter(...)` so the default is the conservative 60/min, then opt-in reads to 300/min. Less code churn; gives the right safe-by-default behavior.

### Finding R8-OFFCHAIN-3 — `parse_user_address` claims to validate network but does not (MEDIUM availability + INFO data-quality)

- **Severity:** LOW–MEDIUM. Mainnet-deploy-blocking.
- **File:Line:** `D:/aegis/api/tx_build.py:849-870`.
- **Description:**
  The docstring at line 850 reads "Parse a user-supplied bech32 address and validate the network." The implementation only calls `pyc.Address.from_primitive(address_str)` and returns the result — no comparison against `AEGIS_NETWORK`.
  On a preprod API instance, a user can submit `addr1q9s6m9d…` (mainnet) and the build path will accept it, then issue Blockfrost UTxO queries against the preprod endpoint using a mainnet bech32. The Blockfrost preprod endpoint either 404s the UTxO query or returns an empty UTxO list, and the build raises a confusing downstream `ValueError("No wallet UTxOs found")`.
  On mainnet deploy this is more dangerous: someone could submit a preprod `addr_test1…` to the mainnet build endpoint, and `addr_test` UTxO queries against mainnet Blockfrost return empty — but for `wallet/sweep/build` (wallet.py:134-212) the network check inside `build_sweep_aegis_tx` (line 166) compares `aegis_address.network` to `destination_address.network`. If the operator passes a destination on the wrong network, the build proceeds and produces a tx the chain will reject after the user signs — wasted wallet popup + key exposure with no clean error.

- **Exploit construction:**
  ```
  curl -X POST https://api-v3.fluxpointstudios.com/api/wallet/sweep/build \
    -H 'Content-Type: application/json' \
    -d '{"aegis_address":"addr_test1qz...","destination_address":"addr_test1qz..."}'
  ```
  Works on the wrong-network instance. Or with two same-network testnet bech32s on a mainnet API instance, the sweep proceeds and the user signs a tx against a non-existent UTxO set.

- **Remediation suggestion:**
  In `tx_build.py:867`, add an explicit network check:
  ```python
  addr = pyc.Address.from_primitive(address_str)
  expected = pyc.Network.MAINNET if AEGIS_NETWORK == "mainnet" else pyc.Network.TESTNET
  if addr.network != expected:
      raise ValueError(
          f"user_address {address_str!r} is on network "
          f"{addr.network!r}; this API instance runs on {AEGIS_NETWORK!r}"
      )
  return addr
  ```
  (Import `AEGIS_NETWORK` from `chain.py`.) Test by submitting a mainnet bech32 to the preprod API and asserting 400.

### Finding R8-OFFCHAIN-4 — `build_sweep_aegis` accepts arbitrary destination_address with no caller authorization (LOW + INFO)

- **Severity:** LOW (no drain — signing requires the in-browser Ed25519 key, which the API doesn't hold). Mostly an info leak + griefing surface.
- **File:Line:** `D:/aegis/api/wallet.py:134-212` + `D:/aegis/api/server.py:1576-1595`.
- **Description:**
  `POST /api/wallet/sweep/build` takes an `aegis_address` and `destination_address` from the request body. Anyone can submit anybody's known aegis_address (these are derived from the user's auto-claim Ed25519 key and surfaced in the frontend UI), with their own attacker-controlled destination. The API will:
  1. Confirm the destination is on the right network.
  2. Query the aegis_address's UTxOs.
  3. Produce a complete unsigned-tx CBOR that drains every UTxO at the aegis_address to the destination.
  The response contains the full tx CBOR, all UTxO refs, and the swept lovelace total. None of this is private data, but the endpoint never verifies the caller IS the holder of the Aegis Ed25519 key for that address. An attacker who can monitor support channels for an aegis_address can pre-build a phishing tx and inject it via a malicious frontend that swaps `destination_address` to the attacker's address. The user signs the legitimate-looking transaction in their Aegis wallet UI and the funds drain to the attacker.
  This is fundamentally a frontend-trust attack but the fact the API never asserts caller authority means a malicious frontend can construct it without any user-visible "this isn't your address" cue.

- **Exploit construction:**
  Cross-site script in the WardensPanel or any other Aegis-served frontend page that calls:
  ```
  fetch('/api/wallet/sweep/build', {method:'POST', body: JSON.stringify({
    aegis_address: '<victim aegis addr>',
    destination_address: '<attacker addr>'
  })}).then(r => r.json()).then(({tx_cbor}) =>
    window.aegisWallet.signTx(tx_cbor, false));
  ```
  Same-origin XSS payload directly drains the victim's aegis wallet. The user sees an Aegis signing prompt for "sweep" which they expect from the WithdrawAll button — same call path, same UI.

- **Remediation suggestion:**
  Layered defense:
  1. Require the `destination_address` to equal a recently-seen funding address (track the last few `fund_aegis_wallet` source addresses per aegis_address; reject if `destination` doesn't match). Stores a tiny ledger of (aegis_address → set[trusted_destinations]).
  2. Force-warn in the frontend: signing flow shows the destination address prominently with a "Is this YOUR wallet?" verification step, blocking until the user clicks an explicit "yes, I'm sending to MY wallet."
  3. Best fix: add a `nonce` field signed by the Aegis wallet ahead of the build request. Server validates the nonce was signed by the aegis_address's payment vkey before building. Requires a small frontend change but completely closes the XSS surface.

  This is not currently exploited as far as I can verify (Aegis frontend doesn't have known XSS today), but the surface should be closed before mainnet deploy alongside the security audit notes that already cover non-custodial flow.

### Finding R8-OFFCHAIN-5 — submit_signed_tx idempotency cache leaks tx hashes via timing (INFO)

- **Severity:** INFO.
- **File:Line:** `D:/aegis/api/tx_submit.py:124-149`.
- **Description:**
  `_submit_cache` is a process-wide dict keyed by canonical tx hash. On a repeat-submit, `_cache_get` returns the cached entry's age and short-circuits BEFORE calling the chain. The response is structured identically (`{"tx_hash":..., "duplicate":true}`) but the round-trip is ~1ms instead of the ~500ms the chain path takes. An external observer who can measure the API's response time can determine whether a tx hash was recently submitted to this server — useful for de-anonymising aegis wallet flows (e.g., correlating an attacker-known tx_id with whether THIS api instance was used to submit it).
  Not a drain. Just a side-channel — chain data is fully public, so this only reveals "did this api instance handle this submit" not "what's in the tx."

- **Remediation suggestion:**
  Move the idempotency cache to a constant-time path (sleep to baseline 200ms before answering). Or remove the in-process cache entirely and rely on the chain's idempotent acceptance behavior. Documentation-only change for now; this is below the bar to ship a code fix for mainnet launch.

## Findings considered but rejected

- **CIP-30 witness merge re-encodes Plutus Data:** Verified `sign_and_submit.ts:220-305` walks the outer map and copies value byte ranges verbatim for every key except 0 (vkey_witnesses). Vkey witnesses ARE round-tripped through cbor-x, but they're `[bytes(32), bytes(64)]` pairs with no Plutus Data, no indefinite-length encoding decisions to preserve. `script_data_hash = blake2b(redeemers || datums || cost_models)` only covers fields 4 (datums) and 5 (redeemers) of the witness set — those are preserved byte-for-byte. SAFE.
- **`_canonical_tx_id` byte-walk bug:** Walked the parser at `tx_submit.py:75-110`. Handles all five length encodings (1-9 byte headers) and correctly slices the body via the consumed bytes count from `cbor2.CBORDecoder.decode()`. Correct.
- **PyCardano cost-model recompute on Plutus V3:** `_recompute_script_data_hash` (tx_build.py:589-656) takes `dict.values()` from the chain context's cost_models — verified Blockfrost preserves canonical operator order in its dict response. Safe vs old 0.13.x alphabetic-sort bug.
- **Ref-script substitution:** Reviewed `_resolve_ref_utxo` (pool.py) and the env vars `AEGIS_POLICY_REF_UTXO`, `AEGIS_POOL_REF_UTXO`, `AEGIS_LP_REF_UTXO`. Substitution would require the attacker to control either the operator deploy or the Railway environment. The on-chain validator's script-hash check would reject a substituted ref-script anyway. Not exploitable.
- **Oracle freshness gaming via AegisSelf failover:** `_get_default_oracle_price` (server.py:1252-1290) falls AegisSelf → Charli3 if AegisSelf raises. Per-policy paths bypass this entirely (they dispatch on the policy datum's bound `oracle_provider`, never falling back). So the failover is purely informational (dashboard/quote endpoint default) — cannot be used to game claim eligibility. The on-chain validator enforces the bound provider regardless.
- **Coverage_amount overflow/underflow:** Pydantic gates `coverage_ada >= 5` (server.py:412) and the lovelace conversion `int(coverage_ada * 1_000_000)` is bounded by Python's arbitrary precision int. No overflow path. On-chain validator enforces `coverage > 0` (V12 fix A-024).
- **Auto-claim Shamir 2-of-3 wallet:** No 2-of-3 Shamir reconstruction code path was located in the API (`grep -rn "shamir\|2-of-3" /d/aegis/api/` returns 0 matches). The mention in the scope appears to be a future or frontend-only construct. Cannot evaluate against absent code.
- **Operator-mode endpoint exposure on production:** `assert_operator_mode` is correctly placed in operator-only flows (init_pool, ref-script publish). The default `AEGIS_OPERATOR_MODE=0` blocks them. Verified.
- **start_time outside validity_range (v8 invariant):** Single `current_slot = now_slot()` reads consumed both by `start_time_ms` and `builder.validity_start` at policies.py:1939-2109, 3905-4134. Both build paths (operator and CIP-30) verified consistent.
