# Vacuumlabs CTF Non-Applicability Proof (R8-PAT-8 + R8-PAT-9)

Verification target: Aegis V12.2 + R7 + R8-DRAIN-1 fix as committed to
`D:/aegis/contracts/` (validators/pool.ak, validators/policy.ak,
validators/lp_token.ak, validators/pool_nft.ak; lib/aegis/{pool,validation}.ak,
lib/aegis/oracle/indigo.ak).

## Methodology

For each pattern I traced the on-chain check that would have to fail open to
let the attacker double-credit a single output or smuggle a second
script-typed UTxO past the validator. I then constructed the most
attacker-favourable transaction shape the validator would accept and checked
whether (a) the constraint is structurally bypassed and (b) the economic
delta favours the attacker. Findings are only raised where BOTH (a) and
(b) hold — a primitive that "passes" the validator but burns the attacker's
own funds is not a finding.

## R8-PAT-8 — Mutual Exclusion Breaking

### Pool team/partner output aliasing (post-R8-DRAIN-1)

R8-DRAIN-1 closes the original Vacuumlabs-style aliasing pair
(team_address vs partner_address) via
`partner_address_not_aliased` at `pool.ak:534–547` invoked in all three
fee-bearing branches: Underwrite (`pool.ak:783–789`), BatchUnderwrite
(`pool.ak:1109–1118`, list-walked over `partner_totals`), and
AcceptCancellation (`pool.ak:1379–1385`). The guard rejects
`partner_address ∈ { team_address, own_address, Script(policy_script_hash) }`.

Are there OTHER privileged-output pairs in the pool validator that could be
aliased to one another? Enumerating the pool's per-branch
`output_to_address_at_least` / fixed-address checks:

| Branch                  | Required output destinations                                                              |
| ----------------------- | ----------------------------------------------------------------------------------------- |
| Underwrite              | (1) pool continuation `own_address+pool_nft`; (2) policy output at `Script(policy_script_hash)+canonical-datum`; (3) `team_address`; (4) optional `partner_address` |
| BatchUnderwrite         | same as Underwrite, with policy and partner outputs aggregated; team check on `team_total` |
| AcceptCancellation      | (1) pool continuation; (2) `team_address`; (3) optional `partner_address`                 |
| ProcessClaim            | (1) pool continuation only                                                                |
| BatchExpireProcess      | (1) pool continuation only                                                                |
| Add/RemoveLiquidity     | (1) pool continuation only                                                                |

The pool continuation is pinned by `own_address AND output_has_nft(output,
datum.pool_nft)` (`pool.ak:597–605`) — its uniqueness is guaranteed by the
one-shot pool NFT (see §R8-PAT-9 below). The policy output is pinned by
`Script(policy_script_hash) + canonical PolicyDatum + lovelace >= coverage`
(`pool.ak:440–473`, `pool.ak:281–369`). These two pins use script
credentials that the protocol controls — they cannot alias `team_address`
(which is a VK credential pinned at `types.ak:624–630`,
`from_verification_key(#"c373…2fe")`).

Could `team_address` alias the pool continuation? `team_address` is a
`VerificationKey` credential; the pool address is a `Script` credential. The
`Address` equality check (`output_to_address_at_least` at `pool.ak:518`)
compares the full record — different credential kinds are unequal.
Therefore the team output can never satisfy the pool continuation's check
or vice versa.

Could `team_address` alias the policy output? Same answer for the same
reason: policy output is at `Script(policy_script_hash)`, team is a VK
address. Structurally non-equal.

Could the policy output satisfy the pool continuation? The policy address
is `Script(policy_script_hash)`; the pool address is `Script(pool_script_hash)`.
Off-chain deployment guarantees these are distinct script hashes (the two
validators have different parameter sets and different bytecode). On-chain
the pool validator binds `own_address` from `self_input.output.address`
(`pool.ak:592`) — a single tx can only consume one pool UTxO (since the
pool_nft is a singleton), so `own_address` is fixed. No aliasing primitive
remains.

**Verdict: NOT APPLICABLE.** All structural pairs are credential-typed-
distinct or singleton-pinned. R8-DRAIN-1 already closed the only VK-vs-VK
pair (team vs partner). The Script-vs-Script pair (pool vs policy) is
deploy-time enforced and additionally re-checked via the NFT-pin on the
pool continuation.

### BatchClaim per-policy payout aggregation

Each consumed policy UTxO in a BatchClaim batch runs `policy_validator`
independently, with this enforcement at `policy.ak:266–268`:

```
let payout_valid =
  sum_lovelace_to_enterprise_pkh(outputs, datum.insured) >= datum.coverage_amount
```

`sum_lovelace_to_enterprise_pkh` (`validation.ak:152–171`) aggregates over
ALL outputs with `payment_credential == VerificationKey(pkh) && stake_credential == None`.
If two policies in the batch share the SAME `datum.insured`, the same
output flowing to that insured is counted toward BOTH policies' `>= coverage`
checks. This is the classic double-satisfaction primitive — at first read it
looks exploitable.

Walking the economics:

1. At Underwrite/BatchUnderwrite time, the pool's `batch_policies_funded`
   (`pool.ak:1074`) requires every new policy output to carry `lovelace >=
   pdat.coverage_amount` (`pool.ak:301–302`). The SUBMITTER funds this
   coverage; the pool only contributes `net_pool_growth = total_premium -
   fee_total_sum` to its own continuation.
2. At BatchClaim time, each policy UTxO holds its own coverage in lovelace.
   The validator requires `policy_utxo_lovelace - coverage_amount` to flow
   back to the canonical pool (`policy.ak:271–287`) and `>= coverage_amount`
   to flow to insured.
3. If two same-insured policies are claimed but only ONE coverage-sized
   output goes to insured, then each policy's claim path forces its
   `policy_utxo_lovelace - coverage_amount` surplus back to the pool. The
   SHORT coverage amount (the duplicate) has nowhere else to go — the pool's
   minimum continuation lovelace is unchanged by the policy validator
   (each policy independently checks pool >= its remainder; the AGGREGATE
   surplus over remainders flows into the pool as a free gift).
4. Net economic effect of the double-credit primitive: insured receives
   `coverage` once (not 2×coverage); the pool gains `coverage` of free
   liquidity it didn't have before. The "attacker" (who must be the insured
   — `insured` is a single VKH so both policies belong to the same wallet)
   LOSES coverage that they pre-funded as the underwriting submitter. The
   pool gains. There is no positive-EV exploit.

Could the attacker construct two policies with different `insured` VKHs
but both controlled by the same person? No — `sum_lovelace_to_enterprise_pkh`
matches on a SINGLE pkh, and policy A's check sums only outputs to A's
insured, policy B's check sums only outputs to B's insured. If insureds
differ, the single-output primitive collapses (one output can only have one
payment_credential).

A secondary concern: does the aggregation surface let an attacker
withhold the pool remainder? `find_canonical_pool_output` (`validation.ak:216–234`)
finds the first output at the pool script address carrying `pool_nft`. The
pool NFT is a one-shot (per `pool_nft.ak`), so there is exactly one such
output. Per-policy check is `output_has_min_lovelace(out, expected_remainder)`.
For two policies sharing the same pool, both checks read the SAME pool
output and each demands `>= remainder_i`. If `remainder_1 == remainder_2 ==
3 ADA` and the actual pool continuation grew by only 3 ADA, both checks
pass even though the pool should have grown by 6 ADA. THIS is a real
aggregation gap.

Walking the economics on this variant:

1. Policy A: lovelace = 100 ADA, coverage = 50 ADA → remainder = 50 ADA must
   flow to pool.
2. Policy B: lovelace = 100 ADA, coverage = 50 ADA → remainder = 50 ADA must
   flow to pool.
3. Attacker sends 50 ADA to insured (satisfies both `>= 50`), and only 50 ADA
   to pool (satisfies both `>= 50`).
4. Where do the remaining `(100 + 100) - 50 - 50 = 100` ADA go? Tx must
   balance — they go to... attacker change output.

If the policy UTxOs hold 100 ADA each (50 coverage + 50 surplus, e.g. the
unspent premium baked into the policy UTxO at Underwrite for liquidity
buffering), then this primitive lets the attacker pocket 100 ADA that the
pool was entitled to.

But: looking at Aegis policy UTxO construction at Underwrite (`pool.ak:301–302`),
the policy output is funded with `>= pdat.coverage_amount`. The off-chain
builder funds it with EXACTLY `coverage_amount` lovelace per spec (no
surplus baked in — the premium flows to the pool's net_pool_growth at
Underwrite, NOT into the policy UTxO). So `policy_utxo_lovelace ==
coverage_amount` and `expected_remainder == 0` for every honest policy.
The `pool_receives_remainder` check has a zero-remainder short-circuit
(`policy.ak:221–222`: `if expected_remainder <= 0 { True }`), so when
remainder is 0 the check is vacuously true and the aggregation primitive
moves zero value. The pool is not drained because the surplus that would
have been drained does not exist.

Could an attacker construct a policy UTxO with surplus to weaponize this?
At Underwrite time the pool's `batch_policies_funded` requires `>= coverage`
on each policy output and the pool's value invariant requires
`cont_output.value == own_value + net_pool_growth` EXACTLY. Any overshoot
on policy outputs is funded by the SUBMITTER (their own funds, not the
pool). So the attacker has to PRE-FUND the surplus they'd later drain via
this primitive — burning their own coverage payment a third time. EV-
negative; no exploit.

**Verdict: NOT APPLICABLE.** Two latent double-satisfaction primitives
exist (same-insured payout aggregation, same-pool remainder aggregation),
but both are economically neutralised by the Aegis funding invariant —
policy UTxOs are funded at EXACTLY coverage_amount with no exploitable
surplus, and the attacker is structurally forced to be the underwriting
submitter whose own pre-funded coverage flows to the pool on each
double-credit attempt.

### Cross-protocol (Indigo/Liqwid/Lenfi)

Aegis interacts with Indigo via REFERENCE INPUT only (`indigo.ak:189–212`).
The Indigo oracle UTxO is never SPENT by an Aegis tx — it is read-only.
Indigo's own validators do not enforce anything on Aegis txs (a reference
input does not trigger the referenced script). Therefore there is no
constraint on the Indigo side that an Aegis output could double-satisfy.

Liqwid and Lenfi integration is OFF-CHAIN only at V12.2 — there are no
on-chain handshakes between Aegis validators and Liqwid/Lenfi scripts.
(LendingPanel front-end is gated behind "Coming soon" pill per task #141.)
No cross-protocol mutual-exclusion surface exists.

**Verdict: NOT APPLICABLE.**

### Verdict: NOT APPLICABLE

Two structural double-satisfaction primitives exist on paper (BatchClaim
same-insured payout, BatchClaim same-pool remainder). Both are economically
neutralised by the V12.2 policy-funding invariant: policies hold EXACTLY
coverage_amount lovelace, so the aggregation gap moves zero value. The
attacker's only options expand the gap by pre-funding it themselves, which
is EV-negative.

## R8-PAT-9 — Multiple UTxO Instances

### Pool validator single-output-at-script enforcement

The pool validator's continuation discovery (`pool.ak:596–605`):

```
let pool_output =
  list.find(
    outputs,
    fn(output) {
      output.address == own_address && output_has_nft(output, datum.pool_nft)
    },
  )
```

This finds the FIRST output at `own_address` carrying `pool_nft`. The NFT
is a one-shot mint (see §"Pool NFT one-shot mint" below) — there is exactly
ONE token with that policy id in existence across all Cardano, and it
lives at the pool script address. An attacker cannot place a second token
under the canonical pool_nft policy because the minting policy can never
emit a second mint (the init UTxO is spent and unrecoverable). Therefore
at most ONE output in any tx can satisfy `output_has_nft(output, datum.pool_nft)`,
making `list.find` and `list.filter | length == 1` semantically equivalent.

What about a SECOND output at `own_address` WITHOUT the pool_nft? The
validator ignores it — `pool_output` only binds the NFT-carrying one.
However, the value invariant (`pool.ak:686`, `pool.ak:864`, `pool.ak:908`,
`pool.ak:966`, `pool.ak:1068`, `pool.ak:1188`, `pool.ak:1317`) is an
EQUALITY: `lovelace_of(cont_output.value) == lovelace_of(own_value) +
net_pool_growth` (or its branch-specific delta). The cont_output is the
canonical (pool_nft-carrying) one. Extra value sent to a "shadow" pool
output at the same address comes from the SUBMITTER (since the tx must
balance and the canonical pool's outflow is pinned by equality), and the
shadow output requires an inline PoolDatum to be later spendable — without
the NFT it cannot satisfy the future pool continuation check, so the
shadow is permanently dust at the pool address. Attacker loses; no exploit.

**Verdict: NOT APPLICABLE.**

### Policy validator single-policy-mint enforcement

In `policy_validator` (`policy.ak:123–413`), each spend invocation
validates ONE policy UTxO (the one matching `own_ref`). The Claim branch
explicitly guards multi-input with `count_script_inputs(inputs,
own_script_hash) == 1` (`policy.ak:159–160`) — preventing the original
F-001 double-satisfaction.

BatchClaim relaxes this to `>= 1` (`policy.ak:237–238`) — by design,
multiple policies CAN be claimed in one tx. The mutual-exclusion analysis
for that branch is in §R8-PAT-8 above; result: no exploit.

For Underwrite-time creation, `pool.ak`'s helpers
`policy_output_matches_underwrite` (`pool.ak:416–480`) and
`batch_policies_match_totals_v12` (`pool.ak:257–379`) enforce that EVERY
output at the policy script address has a canonical datum (pool binding,
oracle pinning, time bounds, lovelace >= coverage). The single-Underwrite
helper additionally enforces `matching_count == 1` (`pool.ak:475–479`) —
exactly one policy output. The batch helper aggregates and binds totals
to redeemer-claimed totals. There is no slack for unchecked policy
outputs.

**Verdict: NOT APPLICABLE.**

### Pool NFT one-shot mint

`pool_nft.ak:47–86` parameterises the minting policy by an `OutputReference`.
The mint is gated by:

```
let init_utxo_consumed =
  list.any(inputs, fn(input) { input.output_reference == utxo_ref })
let one_shot_mint =
  init_utxo_consumed && named_qty == 1 && total_under_policy == 1
```

Once `utxo_ref` is consumed (by the initial pool-bootstrap tx), it can
never be consumed again — UTxOs are spend-once on Cardano. Therefore the
`init_utxo_consumed` clause becomes permanently false for the canonical
pool's deployment, and `one_shot_mint` can never be satisfied again. The
burn path (`total_under_policy < 0`) is the ONLY remaining capability,
which can never produce additional tokens.

`total_under_policy == 1 AND named_qty == 1` together prevent piggy-back
mints of differently-named tokens under the same policy id (caught by
`pool_nft_logic_extra_asset_name_under_policy_rejected` test at
`pool_nft.ak:129`).

**Verdict: NOT APPLICABLE.** The pool NFT is a true one-shot. There can
never be two pool UTxOs.

### lp_token shadow-pool risk

`lp_token_policy` (`lp_token.ak:24–66`) requires the pool script to be
consumed (`pool_is_consumed = list.any(inputs, ...) Script(hash) ==
pool_script_hash`) and the mint quantity to match the redeemer direction.
The actual mint MAGNITUDE is bound by the POOL validator's AddLiquidity
branch (`pool.ak:915–917`): `mint_qty == lp_supply_delta && mint_qty > 0`,
where `lp_supply_delta = new_datum.lp_supply - datum.lp_supply` and
`new_datum.lp_supply` is constrained to `old_lp_supply + calculate_lp_mint(amount,
old_total, old_lp_supply)` by `verify_add_liquidity_datum` (`pool.ak:891–899`,
`lib/aegis/pool.ak:142`).

Could an attacker include two pool inputs (canonical + shadow) and trick
the LP mint into using a stale `lp_supply`? No — only ONE pool UTxO carries
the pool_nft (one-shot), and the pool validator's spend reads `datum` from
`self_input` (`pool.ak:571`). If somehow two pool UTxOs were spent in one
tx, each would run `pool_validator` independently with its own
`self_input` and its own datum. The "shadow" pool would have to satisfy
its own `value_ok` against ITS OWN continuation — which doesn't exist
because the shadow doesn't carry the pool_nft. So either (a) the shadow
has no continuation, failing `expect Some(cont_output)`, or (b) the shadow
carries the pool_nft, which is impossible.

`lp_token` itself just requires "the pool script is consumed" — not "exactly
one pool UTxO is consumed". So in the hypothetical impossible world where
two pool UTxOs exist, lp_token doesn't catch the double-consumption — but
the pool validator does (each instance must produce its own valid
continuation). The composition is safe because the pool's continuation
discovery transitively enforces uniqueness via the NFT.

**Verdict: NOT APPLICABLE.**

### Verdict: NOT APPLICABLE

All four sub-cases trace back to the pool NFT one-shot guarantee
(`pool_nft.ak:53`). With that invariant, every "multiple UTxO instances"
attack collapses: the canonical pool is a singleton, the canonical policy
output is matched-exactly by `policy_output_matches_underwrite`, and
BatchClaim's multi-policy path is intentional and analysed in
§R8-PAT-8.

## Confidence assessment

**High confidence on R8-PAT-9** — the one-shot pool NFT is a hard
structural guarantee, and the validator's continuation discovery via NFT
pin makes the "multiple instances" surface unreachable. The Aiken tests
at `pool_nft.ak:101–155` cover the four edge cases (consumed, not
consumed, two-NFT mint, piggy-back asset name, zero mint).

**Medium-high confidence on R8-PAT-8** — the structural double-satisfaction
primitives in BatchClaim (same-insured payout, same-pool remainder) do
exist on paper, but their exploitability is gated by the V12.2 policy-
funding invariant (`assets.lovelace_of(out.value) >= pdat.coverage_amount`
ENFORCED at Underwrite, with no upper bound enforced — so an off-chain
builder COULD over-fund a policy output, locking attacker funds inside
the policy UTxO). The non-applicability argument rests on no honest
off-chain path emitting over-funded policies AND on the attacker being
EV-negative when they fund their own surplus. If a future change ever
makes the policy-funding `>=` into `==` (tightening the invariant), or
adds explicit per-policy enterprise-output uniqueness, the analysis
becomes ironclad.

**Recommendation (not a finding, defense-in-depth)**: consider tightening
`assets.lovelace_of(out.value) >= pdat.coverage_amount` to `==
pdat.coverage_amount` at `pool.ak:302`, `pool.ak:453`. This would
eliminate the residual aggregation surface entirely. Cost: zero — every
honest off-chain caller already funds with exactly `coverage_amount`.

No findings raised. The Vacuumlabs CTF patterns R8-PAT-8 and R8-PAT-9 are
NOT APPLICABLE to Aegis V12.2 + R7 + R8-DRAIN-1.
