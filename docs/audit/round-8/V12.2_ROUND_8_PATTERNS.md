## Research methodology + sources scanned

This pass deliberately ignored everything previously catalogued in rounds 1–7 and focused on the period **2024-04 → 2026-05**, prioritising:

1. **Cardano ledger/node incidents** that touched production mainnet (chain split, hard-fork edge cases).
2. **Oracle provider incidents** at Charli3 and Orcfax — Aegis consumes both.
3. **Aiken compiler changelogs** (v1.1.17 → v1.1.22) for fixes that change validator behaviour silently.
4. **Cardano CTF “Bank Series” (vacuumlabs)** — adversary-curated patterns the audit community treats as canonical 2024–2025 footguns.
5. **Cross-protocol manipulation** observed against Indigo, DJED, and similar synthetic/CDP shapes.

**Sources scanned (all URLs included inline below):** Intersect incident report (Nov 2025), Cardano Foundation blog, CryptoSlate / CoinDesk / CryptoBriefing technical write-ups, Charli3 Medium incident report (Apr 2024), Orcfax suspension notice (May 2024), `aiken-lang/aiken` CHANGELOG.md, `vacuumlabs/cardano-ctf` README, IntersectMBO/cardano-ledger Conway CDDL, Indigo/Pyth integration coverage, DJED depeg coverage (Oct 2025).

## Patterns found

### Pattern R8-PAT-1: Oversized-hash deserialization in delegation certificate (Cardano node 10.3.x–10.5.1)
- **Source:** https://intersectmbo.org/news/incident-report-network-partition-analysis-and-resolution-strategy ; https://cryptobriefing.com/cardano-chain-split-exploit/ ; https://cryptoslate.com/cardano-split-in-two-by-a-single-transaction-lessons-for-eth-and-sol-client-diversity/ ; https://www.coindesk.com/markets/2025/11/23/cardano-temporarily-splits-into-two-chains-after-attacker-uses-ai-generated-script-to-exploit-a-known-bug ; https://cardanofoundation.org/blog/november-2025-cardano-shows-resilience
- **Date:** 2025-11-21, hotfix v10.5.3 within ~3 hours, full network reconvergence ~14.5 hours later.
- **Technical description:** A delegation certificate carrying an **oversized hash field** bypassed a deserializer in `Hash`-handling code introduced in 2022 but only reached by a code path activated in 10.3.x. Older nodes rejected the tx; 10.3.x–10.5.1 accepted it. Chain forked. Bug lived **below** Plutus — in ledger validation of certificate witnesses, not in script evaluation. **No Plutus script ever saw the malformed cert.**
- **Aegis applicability: PARTIAL.** Aegis Plutus V3 validators are unaffected because the exploit lived in node-level certificate validation, not in `ScriptContext`. **However**, two Aegis-specific second-order risks remain:
  - **(a) Operator-node version pinning.** Aegis depends on a single `cardano-node` (preprod Pi today, mainnet TBD). If our operator node sits on a future analogous “dormant deserializer” path while the rest of the network reconverges on a different branch, Aegis would publish AegisSelf prices, submit claims, and accept Underwrite txs **against the wrong chain** for the duration of the partition. Pi-deploy runbook (`reference_local_runbooks.md`) does not currently specify a node-version monitor / dual-node quorum.
  - **(b) Submit-API blast radius.** During the 14.5-hour window, exchanges paused deposits but `/api/tx/submit` would have continued to relay. A user signing a Claim during partition could have it confirm on the poisoned chain, then disappear at rollback. Aegis has no chain-tip divergence detector.
- **Where in Aegis:** `aegis-publisher` service (NSSM), `/api/tx/submit` (Railway), Pi node and any future mainnet node.

### Pattern R8-PAT-2: Single-source oracle collapse via API mis-pairing (Charli3 April 2024)
- **Source:** https://oraclecharli3.medium.com/charli3-incident-report-989f12a9e38c
- **Date:** 2024-04-06 → 2024-04-08 (~11 hours bad data on DJED/USD).
- **Technical description:** Blockfrost began returning **`aggstate` datums inside Oracle NFT UTxOs and vice-versa**, with constructor IDs swapped (`Expect 122, got 123`). Charli3 attempted mitigation by **removing Blockfrost** from data-source rotation — which dropped DJED feed to **two** sources (Sundaeswap + Wingriders). With <3 sources, the median function cannot reject outliers; Sundaeswap then transmitted `0.005735` for 20 minutes and the 2-source median **randomly picked the corrupt value 50% of the time**. Charli3 fix: hard-coded minimum of 3 data sources and a circuit-breaker that suspends a feed if it drops below 3.
- **Aegis applicability: YES — direct match on three primitives.**
  1. **Multi-oracle aggregation has the same outlier-rejection floor.** Aegis (V12.2 R7) consumes Charli3 + Orcfax + AegisSelf. If any one provider produces unreliable data and we **degrade gracefully** to the remaining two, our aggregator inherits the exact failure mode Charli3 hit: median-of-two has no outlier rejection. This is the same primitive at a higher level of abstraction.
  2. **Constructor-ID swap is exactly the class of bug Aegis CDP/Indigo observer is vulnerable to.** Indigo CDP datum and our own pool datum share a project-wide encoding convention (Constr_0 `d8 79 9f...ff`, per `reference_aegis_v8_cbor_canonical.md`). If an upstream wallet or off-chain builder swaps which datum lands in which UTxO, our observer reads the wrong datum into the wrong validator branch.
  3. **Sundaeswap-as-data-source-then-outlier echoes our reliance on protocol observers** (Indigo, Liqwid, Lenfi). The “bad price gets through because there are too few sources to outlier-reject” pattern applies to **any** Aegis feature that observes a single off-chain protocol state.
- **Where in Aegis:** `api/server.py` per-policy oracle dispatcher (post-R7 refactor), `oracles/aggregator.py`, AegisSelf publisher single-source mode, Indigo CDP observer (`pool.ak` BatchClaim arm), Liqwid/Lenfi observer paths.
- **Round-8 hypotheses to test:** (i) Force a 1-of-3 oracle-down state and verify the aggregator rejects the txn rather than silently medianing 2. (ii) Confirm Aegis emits a circuit-break feed status when ≤2 providers are healthy. (iii) Verify Indigo CDP datum constructor IDs are checked explicitly (not pattern-matched permissively).

### Pattern R8-PAT-3: Orcfax COOP Plutus-Chain-Index suspension (May 2024)
- **Source:** https://medium.com/@orcfax/orcfax-feed-suspension-and-protocol-upgrade-a45709dafb56
- **Date:** 2024-05-15. Feed was **voluntarily suspended**, no financial loss.
- **Technical description:** A failure in the Plutus-Chain-Index module of Orcfax’s COOP forced suspension of mainnet ADA/USD publishing. The off-chain indexer that maps UTxOs → feed state stopped producing reliable references, but the on-chain validator was untouched.
- **Aegis applicability: PARTIAL.** This is the **stale-feed-but-on-chain-validator-OK** pattern. Aegis already has freshness checks (Round-6 fix series). But the lesson is that an oracle provider can voluntarily stop publishing — and Aegis Underwrite/Claim must remain economically safe during such suspension. **Round-8 hypothesis:** can an adversary front-run a Charli3/Orcfax voluntary suspension by buying low-premium policies in the final hour, when the dispatcher is still serving cached prices? Verify per-policy dispatcher honors observed feed timestamp, not provider service status.

### Pattern R8-PAT-4: Aiken v1.1.19 — PlutusData CBOR-dependent comparison
- **Source:** `aiken-lang/aiken` CHANGELOG, v1.1.19, 2025-07-28 — “PlutusData comparison in the UPLC VM shouldn’t rely on CBOR encoding.”
- **Date:** 2025-07-28 patched.
- **Technical description:** Prior to v1.1.19, `==` on two `Data` values inside a validator compared their **CBOR serialization** rather than their semantic structure. Two semantically-equal values that disagreed on indefinite-vs-definite list form, map ordering, or integer minimal encoding would compare **unequal** inside the validator. Conversely, two semantically-different values producing identical CBOR via canonicalization would compare **equal**.
- **Aegis applicability: YES — high-priority Round-8 check.**
  - Aegis has the **explicit invariant** that Plutus Data must NOT be canonicalized (`reference_cip30_sign_submit.md`, `reference_aegis_v8_cbor_canonical.md`). Wallets and the relay both round-trip raw bytes. **Any Aegis Aiken code that uses `==` on `Data`** built ≤ v1.1.18 may have absorbed comparisons that flip under wallet re-encoding.
  - Aegis memory pins Aiken version `aiken 351/351 tests`. **Confirm aiken --version on the V12.2 R7 build; if < v1.1.19 the pool/policy/aegis_self validators must be rebuilt and rehashed.**
- **Where in Aegis:** every `expect Some(d) = ...; d == expected` pattern in `pool.ak`, `policy.ak`, `aegis_self.ak`, `indigo_observer.ak`.
- **Round-8 action:** grep validators for `Data` equality; if any exist, rebuild on ≥ v1.1.19 and verify the rotated script hash matches the deployed hash. If it doesn’t, the deployed validator carries the buggy comparison.

### Pattern R8-PAT-5: Aiken v1.1.22 — code-gen interner FreeUnique under optimisation
- **Source:** `aiken-lang/aiken` CHANGELOG, v1.1.22, 2026-05-15 — “Fix code generation interner to avoid FreeUnique caused by optimisations.”
- **Date:** 2026-05-15 (patched **one day after this report**).
- **Technical description:** Optimiser produced bytecode with dangling `FreeUnique` references — a class of bug where the validator **compiles** and **passes some test cases** but produces an evaluator error or, worse, silently corrupts a branch under specific input shapes.
- **Aegis applicability: YES — must verify build provenance.**
  - V12.2 R7 was built **before** 2026-05-15. If our build environment has been pulling unpinned `aiken`, an interim version between the introduction of the bug and its fix may have shipped corrupted bytecode into our preprod reference scripts.
  - The `aiken 351/351` greenness only proves the test cases pass — it does **not** prove every reachable branch evaluates correctly.
- **Where in Aegis:** every published reference script (policy `2e4eecf5…`, pool ref `6f277e8d…#0`, lp ref `54df7a1a…#0`, policy ref `aa611f72…#0`).
- **Round-8 action:** pin aiken version in `aiken.toml` + lockfile, rebuild on v1.1.22, diff blueprint hashes against deployed. Any drift = re-deploy.

### Pattern R8-PAT-6: Aiken v1.1.22 — large negative bigint round-trip in `Data::integer`
- **Source:** `aiken-lang/aiken` CHANGELOG, v1.1.22, 2026-05-15.
- **Technical description:** Large-magnitude negative integers round-tripped through `Data::integer` lost precision or changed sign.
- **Aegis applicability: PARTIAL.** Aegis economics use positive lovelace amounts and positive prices. The only path where a negative bigint could enter is **slot delta arithmetic** (oracle freshness check: `now - feed_ts`) or **net-PnL on cross-protocol claim**. If freshness math ever underflows (clock-skew, replay attempt), a buggy compare could flip a stale-feed reject into accept.
- **Round-8 action:** add a property test for `feed_ts > now` (negative-skew) on the freshness path; confirm aiken ≥ v1.1.22.

### Pattern R8-PAT-7: Aiken v1.1.22 — list-pattern empty-check removed under `-t silent`
- **Source:** `aiken-lang/aiken` CHANGELOG, v1.1.22, 2026-05-15 — “Fix compiler removing empty list checks with `-t silent` for list patterns containing only discards.”
- **Technical description:** Optimiser dropped the empty-list guard for `[_, ..]` patterns when tracing was disabled. A validator that pattern-matches `[first, ..rest]` on an expected-non-empty input would, post-optimisation, accept the empty list and bind `first` to a runtime-undefined value.
- **Aegis applicability: YES.** Aegis production builds use `-t silent` to keep mainnet script size minimal. **Any** `[head, ..]` pattern on script outputs, redeemer fields, or observer-decoded lists is a candidate. The BatchUnderwrite branch in particular pattern-matches lists of policy outputs.
- **Where in Aegis:** `pool.ak` BatchUnderwrite branch, BatchClaim Indigo arm (`reference_batch_claim_pattern.md`), any list comprehension over `tx.outputs`.
- **Round-8 action:** static-grep for `[..]` patterns; rebuild on ≥ v1.1.22 with `-t silent`; diff blueprint hashes.

### Pattern R8-PAT-8: vacuumlabs Cardano CTF Bank Series — Mutual Exclusion Breaking via tx-field manipulation
- **Source:** https://github.com/vacuumlabs/cardano-ctf — Bank challenges 03 (and the meta-pattern across 03/04/05).
- **Date:** Bank series published 2024–2025 by the Vacuumlabs auditing team.
- **Technical description:** Two same-script UTxOs in one transaction, each checking some subset of tx fields independently, can be satisfied simultaneously by a single output that both reference. Generalises the 2022 double-satisfaction pattern to **field-level** rather than value-level mutual exclusion (e.g., signatures, mint fields, validity range).
- **Aegis applicability: YES — exactly the BatchUnderwrite + Indigo observer composition risk.**
  - Aegis V12.2 R7 ships a **BatchClaim Indigo arm**. A batch txn touches the pool validator once but processes N Indigo CDPs. If the per-CDP observer check reads only fields that are **not** uniquely-pairing (e.g., reads `tx.signatories` to authorize a per-CDP action, but the pool branch separately reads the same `tx.signatories` to authorize batch-init), one signature can satisfy both branches when it shouldn’t.
  - The pool validator + policy validator + Indigo observer in a single tx is a triangle. Each side likely checks a subset of tx fields. Round-7 already found R7-B (BatchClaim non-exhaustive switch); Round-8 should specifically construct **same-output-double-credited** test cases.
- **Where in Aegis:** `pool.ak` BatchUnderwrite + BatchClaim, `policy.ak` paired with both branches, `indigo_observer.ak`.
- **Round-8 action:** for each pair (pool, policy), (pool, indigo), (policy, indigo), build a tx where one party’s satisfying output also satisfies the other party’s constraint. R7 fixed the non-exhaustive Indigo switch; R8 should test field-level mutual exclusion.

### Pattern R8-PAT-9: vacuumlabs CTF — Multiple UTxO Instances under one tx
- **Source:** https://github.com/vacuumlabs/cardano-ctf — Bank challenge 10.
- **Date:** 2024–2025.
- **Technical description:** A contract designed under the implicit assumption of one input/output of its own kind breaks when an attacker spends multiple UTxOs of the same script in one transaction. Per-output invariants pass; cross-output invariants are unchecked.
- **Aegis applicability: YES.** The Aegis pool is a singleton-UTxO pattern (one pool UTxO, identified by AEGIS_POOL_V12_2_R7 NFT). The validator presumably enforces “exactly one pool input, exactly one pool output.” **But policy UTxOs are not singletons** — many concurrent policies exist. If the policy validator pattern-matches `Some(out) = find ...` rather than enumerating all outputs at this script address, a malicious tx can spend two policy inputs and only fund one continuation output.
- **Where in Aegis:** `policy.ak` — confirm it requires `outputs_at_script == 1` for both inputs and outputs, not just `find`.
- **Round-8 action:** craft a 2-input-1-output policy spend; observe whether the validator catches it.

### Pattern R8-PAT-10: Oracle-driven CDP/synthetic stress (DJED October 2025 depeg)
- **Source:** https://crypto.news/cardanos-djed-stablecoin-faces-unminting-and-depegging-challenges-amid-reserve-ratio-decline/ ; https://www.ccn.com/news/crypto/defi-stablecoins-breaking-every-depeg-2025/ ; https://thecryptobasic.com/2025/10/14/cardano-founder-says-djeds-strong-two-year-99-stability-record-is-magical/
- **Date:** 2025-10-10. DJED briefly fell to $0.55 and recovered within ~5 hours.
- **Technical description:** DJED’s on-chain unminting math relies on an oracle ADA/USD price. A sharp ADA crash (Trump-tariff-driven 10/10 sell-off) caused the reserve ratio to collapse and DJED to depeg. COTI/COTI Labs froze new deposits during the dislocation.
- **Aegis applicability: YES.** Aegis sells **DJED depeg cover** as one of the 4 stablecoin-depeg products. The 10/10 event proves the trigger is **real**, but also that resolution can be **5 hours** — well inside our claim window. Two risks:
  1. **Adversarial Underwriting**: an attacker who observes ADA crash starting could rush-buy DJED-depeg cover **before our publisher’s next AegisSelf push**, then claim minutes later when the oracle catches up. This is the classic “oracle lag = free option” attack.
  2. **Claim-during-recovery**: if the trigger fires for 5 hours and recovers, a slow honest claimant may file post-recovery and be denied; a fast attacker pre-positions to claim during the window. Verify that Aegis trigger uses **observed feed at policy slot**, not “current” feed.
- **Where in Aegis:** depeg cover validator + AegisSelf publisher cadence + freshness window.
- **Round-8 action:** simulate ADA crash + recovery against preprod. Confirm (i) Underwrite during oracle-lag is rejected, and (ii) Claim uses snapshotted feed at trigger slot, not at claim-submit slot.

### Pattern R8-PAT-11: Indigo + Pyth-pull integration (May 2026)
- **Source:** https://dailycoin.com/high-speed-oracle-goes-live-on-cardano-targeting-defis-silent-killer/ ; https://www.bitget.com/amp/news/detail/12560605414156
- **Date:** May 2026. Indigo integrating Pyth pull-based feeds for iAssets.
- **Technical description:** Indigo CDPs now (or imminently) use **pull-based** Pyth Pro prices at the exact moment of user interaction, rather than the older Charli3 push model. This raises the cost of stale-price arbitrage against Indigo, but it changes the **datum shape** Aegis’s Indigo observer reads.
- **Aegis applicability: YES — operational risk, not a vulnerability yet.** Our Indigo observer arm was written against the prior Charli3-pushed Indigo CDP datum. If Indigo silently migrates a subset of CDPs to a Pyth-shaped datum, our observer may either reject valid CDPs (DoS) or accept malformed CDPs (decode mis-pairing — same shape as R8-PAT-2).
- **Where in Aegis:** `indigo_observer.ak` + Wave 1.5 Indigo datum + canonical-address research (#162).
- **Round-8 action:** pull current Indigo CDP datums from mainnet and verify our V12.2 R7 decoder still type-checks against the on-chain encoding. Add explicit Constr-ID assertions, not lenient pattern matching.

### Pattern R8-PAT-12: AI-generated exploit primitives (Cardano chain split attacker used Claude/AI for the malformed tx)
- **Source:** https://www.theblock.co/post/380056/hoskinson-involves-fbi-after-developers-careless-experiment-splits-cardano-blockchain ; https://www.coindesk.com/markets/2025/11/23/cardano-temporarily-splits-into-two-chains-after-attacker-uses-ai-generated-script-to-exploit-a-known-bug
- **Date:** 2025-11-21.
- **Technical description:** Attacker (“Homer J”) claimed to have used AI-generated terminal commands to construct the malformed delegation cert. Whatever the truth of the claim, the broader pattern stands: **LLM-assisted exploit generation against open-source primitives is now operationally common.** A would-be attacker with the Aegis aiken source + the public V12.2 R7 spec + an LLM can iterate exploit candidates far faster than Round-7 manual brainstorming.
- **Aegis applicability: YES — meta-pattern, not a primitive.** Aegis publishes (i) full Aiken source in `aegis-contracts` mirror, (ii) the V12.2 spec, (iii) every red-team report in repo. This is correct — security-through-obscurity is bad — but Round-8 should include an explicit **LLM adversary cycle**: feed Claude/GPT the V12.2 source and ask it to enumerate edge cases. We already do this for code review; Round-8 should formalize it for **adversarial spec interpretation** (find an interpretation of the spec where a transaction the spec considers invalid is in fact accepted by the compiled validator).
- **Where in Aegis:** the whole repo, but particularly any spec-vs-implementation gap.
- **Round-8 action:** one structured LLM-adversary pass on the V12.2 R7 PR diff + spec, asking specifically for spec-vs-code drift.

## Patterns I evaluated and rejected as not applicable to Aegis

- **Cardano CIP-30 wallet witness drop bugs (Eternl/Lace/Vespr/Nami 2025).** No specific 2025 disclosure surfaced in this pass beyond what Aegis already encoded in `reference_cip30_sign_submit.md` (byte-form witness merge, no Plutus Data canonicalization). Coverage is current.
- **PyCardano cost-model alphabetic sort (0.13.x).** Already pinned in Aegis memory as `reference_pycardano_pinned_costmodel_bug.md` and fix landed in `tx_build.py`. Not new.
- **Minswap LP-token unauthorized mint (March 2022 WingRiders disclosure).** Pre-dates 2024 cutoff. Aegis has no LP minting policy of this shape — our LP NFT is single-mint at pool init.
- **CIP-30 mobile deep-link bridge bugs.** Aegis-authored CIP (#170-#174) — not an exploit pattern against Aegis but a spec under our authorship.
- **Cardano Wanchain bridge price manipulation 2025.** No disclosed incident. Aegis does not currently consume bridged-asset prices.
- **DeFi reentrancy (general).** eUTxO model precludes reentrancy in the Solidity sense. Confirmed; not applicable.
- **MEV / front-running on Cardano.** Deterministic fees + no public mempool keep this economically uninteresting on Cardano (per cexplorer / ainvest 2025 coverage). Aegis Underwrite is not a front-runnable trade in the AMM sense; covered.
- **GitHub CVE-2026-3854 (March 2026).** GitHub.com RCE — affects supply chain of repo hosting, not Aegis on-chain code. Mitigation = standard hygiene; not in scope.
- **LangChain LangGrinch CVE-2025-68664.** Affects AI-agent secret leakage in serialization, not Aegis (T-backend already migrated to Kimi K2.6 per memory). Not applicable.

## Confidence level on coverage

**High** for: Cardano-mainnet ledger incidents, Charli3/Orcfax oracle incidents, Aiken compiler changelog through v1.1.22 (latest as of report date 2026-05-14, fix landed 2026-05-15 — the timing is fortuitous), Cardano CTF Bank Series.

**Medium** for: Plutus V3 / Conway era ledger edge cases (the post-Conway disclosed CDDL fixes are well-documented; what we don’t have visibility on is **silently-fixed** ledger bugs that never got public write-ups).

**Lower** for: private bug-bounty findings at Liqwid / Indigo / Lenfi / Minswap — these protocols all run bug-bounty programmes (Lenfi $20k per Catalyst F10), and undisclosed findings could overlap with patterns Aegis shares. Recommend a direct outreach to TxPipe + Anastasia Labs + Vacuumlabs auditing for any Cardano-DeFi-shape findings they’re willing to share pre-mainnet.

**Not covered (acknowledged gap):** This pass found no public 2025–2026 disclosures specifically against Liqwid, Lenfi, Aada, SundaeSwap, or Wingriders. Either (i) those protocols have had a clean year, (ii) findings exist but under embargo, or (iii) my queries missed them. Round-8 should not assume absence of evidence = evidence of absence here.
