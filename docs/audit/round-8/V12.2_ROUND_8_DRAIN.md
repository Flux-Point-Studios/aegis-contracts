## NEW findings (Round 8)

### Finding R8-DRAIN-1 — Team fee captured by single output when `partner_address` aliases any already-required address

**Severity:** **MEDIUM (fee bypass; team-revenue capture, not pool drain).** Up to 20% of every protocol fee diverted. Scales linearly with premium. Hits Underwrite, BatchUnderwrite, AND AcceptCancellation symmetrically.

**File:Line:**
- `validators/pool.ak:715-716` (Underwrite team check)
- `validators/pool.ak:724-734` (Underwrite partner check)
- `validators/pool.ak:1047-1052` (BatchUnderwrite team check)
- `validators/pool.ak:1059-1065` (BatchUnderwrite partner check)
- `validators/pool.ak:1285-1286` (AcceptCancellation team check)
- `validators/pool.ak:1293-1303` (AcceptCancellation partner check)
- Root primitive: `validators/pool.ak:510-521` (`output_to_address_at_least`).

**Description.** `output_to_address_at_least` is `list.any(outputs, fn(o) { o.address == addr && lovelace_of(o.value) >= required })`. The validator calls it independently for `team_address` and for the new policy's `partner_address`. There is no check that:
(a) `partner_address != team_address`,
(b) the team output and partner output are DISTINCT outputs in the tx,
(c) the total of distinct team-or-partner outputs equals `fee_total`.

Therefore, when a hostile builder sets the new policy's `partner_address` to any pre-existing required-output address — most directly `team_address`, but also `pool_address` (the canonical pool continuation) or the user's own change address — the SAME output simultaneously satisfies BOTH `team_output_funded` AND `partner_output_funded`. The user keeps the `partner_cut` lovelace as change.

The pool's `value_ok` invariant (`cont == own + net_pool_growth`) is still enforced exactly, so the LP is NOT short-changed; only the team is. But team revenue is real protocol revenue, and the cap is 20% of `fee_total` per policy.

**Exploit construction (concrete tx-level).**

Pool state: `protocol_fee_bps = 200`, `partner_share_cap_bps = 2_000`. Pick a premium where silent-absorb does NOT kick in: e.g., `premium = 1_000_000_000` (1000 ADA), `coverage = 10_000_000_000` (10k ADA, well under 50× ratio cap).

Hybrid math:
- `fee_total = max(2_000_000, 1_000_000_000 × 200 / 10_000) = max(2_000_000, 20_000_000) = 20_000_000` lovelace (20 ADA).
- `partner_cut_raw = 20_000_000 × 2000 / 10_000 = 4_000_000` lovelace (4 ADA) ≥ `min_utxo` → `partner_cut = 4_000_000`, `team_cut = 16_000_000`.
- `net_pool_growth = 1_000_000_000 − 20_000_000 = 980_000_000`.

**Honest tx outputs (5 required):**
1. Pool continuation: `own.lovelace + 980_000_000` + AEGIS_POOL NFT + new PoolDatum.
2. Policy output at `policy_script_hash`: `≥ coverage` (10 ADA = `coverage_amount`) + PolicyDatum carrying `partner_address = Some(<honest_partner_addr>)`, `partner_share_bps = 2000`.
3. Team output: `team_address`, ≥ 16 ADA (`team_cut`).
4. Partner output: `<honest_partner_addr>`, ≥ 4 ADA (`partner_cut`).
5. User change.

**Exploit tx outputs (4 outputs — partner output omitted):**
1. Pool continuation: same.
2. Policy output: same EXCEPT `partner_address = Some(team_address)`. (`partner_share_bps = 2000` still.)
3. Team output: `team_address`, ≥ 16 ADA. (UNCHANGED from honest.)
4. User change: 4 ADA larger than honest path.

Validator check at line 715: `output_to_address_at_least(outputs, team_address, team_cut = 16 ADA)` → `list.any` hits output #3 (16 ADA ≥ 16 ADA). Pass.

Validator check at lines 724-732: `Some(team_address) → if 4_000_000 > 0 then output_to_address_at_least(outputs, team_address, 4_000_000)` → `list.any` ALSO hits output #3 (16 ADA ≥ 4 ADA). Pass.

`partner_share_in_bounds`: `2000 >= 0 && 2000 <= 2000` → Pass.
`partner_consistency`: `Some(_) → True` → Pass.
`donation_ok`: 0.5 ADA donation required (`1000 × 200 / 10_000 × 2_500 / 10_000`); user pays via Conway body field. Pass.
All other invariants identical to honest path.

**Net effect.** User spends `premium − partner_cut = 996_000_000` of new lovelace (the 4 ADA difference is change). Team receives `team_cut = 16_000_000` instead of `team_cut + partner_cut = 20_000_000`. Pool receives `net_pool_growth = 980_000_000` (unchanged). LP unaffected.

**Per-cycle attacker gain:** `partner_cut` = up to 20% of `fee_total`. At 1000 ADA premium = 4 ADA. At 10 000 ADA premium = 40 ADA. Scales linearly. Attack cost: ~0 marginal (same tx_fee as honest underwrite). Loss-to-cost ratio: very high once premium > 100 ADA.

**Variant 1 — alias to `pool_address`.** Setting `partner_address = Some(pool_address)` is even quieter: the pool's continuation output (already required) is at `pool_address` and carries `net_pool_growth + own.lovelace >> partner_cut`. So `list.any(outputs, ... == pool_address && >= partner_cut)` trivially passes. No team output even needs to be enlarged. Same 4 ADA per-tx capture.

**Variant 2 — alias to user's own change address.** The user's tx already emits change to themselves (≥ min_utxo); if the change is ≥ partner_cut (it is, in the exploit path), then `partner_output_funded` checks pass against the user's own change output. Same capture.

**Variant 3 — BatchUnderwrite aggregation.** In `batch_policies_match_totals_v12` (pool.ak:334-347), each policy that has `partner_address = Some(addr) && partner_cut_i > 0` is `accumulate_partner`-ed into `partner_totals`. If TWO policies in a batch both set `partner_address = Some(team_address)`, then `accumulate_partner` collapses them into one entry `(team_address, sum_of_partner_cuts)`. The check at line 1059-1065 then requires ONE output at team_address ≥ that summed value — which the team's `team_total` output already satisfies as long as `team_total >= sum_of_partner_cuts`. Since `team_total = Σ team_cut_i` and team_cut_i = fee_total_i − partner_cut_i, we have `team_total = fee_total_sum − partner_totals_sum`. For partner_totals_sum ≤ 20% × fee_total_sum, team_total ≥ 80% × fee_total_sum ≥ 4× partner_totals_sum. So team_total ≥ partner_totals_sum always; the team output satisfies BOTH checks. Same exploit, batched, no per-policy splitting required.

**Variant 4 — AcceptCancellation.** Same primitive, on cancel-path `fee_total_cancel`. A user who underwrites with `partner_address = Some(team_address)` AND `partner_share_bps = 2000` then cancels within the 1h window captures the partner_cut on the cancel-fee split as well. Capture per cycle: 2× partner_cut (Underwrite + Cancel). At `premium = 1000 ADA`, `fee_total_cancel = max(2 ADA, 100 ADA × 200/10000) = 2 ADA` (cancellation_fee = 10% of premium = 100 ADA → raw fee = 2 ADA → fee_total_cancel = 2 ADA, `partner_cut_cancel_raw = 0.4 ADA < min_utxo` → absorb → partner_cut = 0). So Variant 4 captures 0 on the cancel-leg, only on the Underwrite leg. Hybrid floor accidentally protects the cancel leg here.

**Why prior rounds missed it.** Round 4-6 reviewed the partner mechanism but focused on the `partner_address` "self-pwn" trust model (caller-supplied = caller's risk) — the doc comment at `types.ak:142-157` frames the partner field as an "off-chain UX concern." That framing led to no validator-side check on aliasing. The walker correctness was verified for the bps-cap and non-negativity (R6 confirmed `partner_share_in_bounds && partner_consistency`), but uniqueness/disjointness of the team and partner output addresses was never tested. R7 added 6 tests targeting R7-A/B/C, none of which exercise aliasing.

**Remediation suggestion.** Either:
1. **Reject `partner_address == Some(team_address)`** at Underwrite/BatchUnderwrite/AcceptCancellation. One additional predicate per branch. Trivially compatible with the existing `partner_consistency` check. **Recommended.** Add tests pinning rejection.
2. **Require strict output disjointness**: enforce that the team output and partner output are at different `output_reference` indices (i.e., distinct outputs). Slightly more code; not necessary if (1) covers all aliases.
3. **Equality-form the team/partner output checks**: require `output_to_address_at_least(team_address, team_cut)` AND `Σ lovelace_at_team_address == team_cut + (partner_cut if partner_addr == team_address else 0)`. Painful arithmetic.

The simplest fix is **Option 1**: add `partner_address != Some(team_address)` to `partner_consistency` (rename to `partner_consistency_and_non_aliasing`). Variants 1-3 also need rejection of `pool_address` and the canonical pool continuation by extension — the cleaner rule is: **`partner_address` MUST NOT be the team address, the pool's address, OR the policy validator's address**. Three string-equality checks.

I expect the fix to land as a one-line predicate in each of the three branches (3 lines total) plus 3 regression tests in `lib/aegis/test_helpers/security_tests.ak`. No new types, no off-chain change required (off-chain builders only ever set `partner_address` to legitimate partner wallets).

### Finding R8-OBS-1 — Dead helper `floor_to_min_utxo` is shipped in `pool.ak`

**Severity:** INFO. Code hygiene, not exploitable.

**File:Line:** `validators/pool.ak:492-498`.

**Description.** The helper `floor_to_min_utxo(amount) -> if amount > min_utxo_lovelace { amount } else { min_utxo_lovelace }` is defined in the validator file but never called (V12.2 spec moved the floor INSIDE `calculate_fee_total`, making this helper redundant). Aiken compiles it into the script (unused private fns are still emitted), wasting a few bytes of script size but not a true exec-cost issue because dead code is never branched into.

**Concrete impact.** None. The validator's emitted CBOR is marginally larger than necessary.

**Remediation suggestion.** Delete `pool.ak:492-498`. One-line removal, hash rotation, all 351 tests should still pass.

## Findings I considered but rejected (with reason)

**1. Indigo `(Indigo, Indigo)` arm in `batch_oracles_uniform` (R7-B follow-up).** I read `policy.ak:84-98` line-by-line. The `(Indigo, Indigo) -> True` arm is present (`policy.ak:96`). The `_ -> False` fallthrough is preserved. Cross-pair tuples like `(Charli3, Indigo)` correctly route to the fallthrough. **No tuple-pattern bypass found.** Tests pinning this: `dispatcher_indigo_branch_compiles` (oracle.ak:242), `is_canonical_accepts_indigo_*` (oracle.ak:303-333), `indigo_disjoint_from_aegis_self` (types.ak:973). Patch complete.

**2. Min-premium drain via re-underwrite cycle (R7-A variant).** Considered: underwrite at premium = 2 ADA, immediately re-underwrite using the same wallet. Each cycle: at Underwrite, pool grows by `net_pool_growth = 2 ADA − 2 ADA = 0`. Pool delta per Underwrite is zero — no LP loss on the Underwrite leg. The LP loss is ONLY on the cancel leg (3.8 ADA per cycle, as documented in R7-A). Re-underwriting without canceling first does NOT compound the loss because each new Underwrite is value-neutral. The cycle has to include a Cancel to extract the 3.8 ADA. Bandwidth-bounded by tx-fee economics — same analysis as R7-A. **Not a new finding; same as R7-A on preprod (min_premium = 2 ADA); fully neutralized on mainnet (min_premium = 100 ADA).**

**3. BatchUnderwrite walker with negative per-policy coverage/premium.** Considered: policy A (cov=99 ADA, prem=100 ADA) + policy B (cov=−1 ADA, prem=−10 ADA), redeemer totals (cov=98, prem=90). Walker accumulates per-policy sums; redeemer total positivity check (`total_coverage > 0 && total_premium > 0`) passes; `funded_ok` requires `cov_sum == 98`; `value_ok` requires pool grows by `total_premium − fee_total_sum`. Aiken integer math floors-toward-negative-infinity on `calculate_protocol_fee(−10 ADA, 200) = −200_000` lovelace; `math.max(2_000_000, −200_000) = 2_000_000`. Each per-policy fee_total floors to `min_utxo`, so `fee_total_sum = 4 ADA`, `net_pool_growth = 86 ADA`. Active_coverage grows by 98 ADA. Policy B is permanently stranded (its coverage_amount is negative → Claim/Expire payout-positivity checks reject; AcceptCancellation `bounds_ok` rejects via `refund_amount >= 0`). No drain — attacker pays full premium for full coverage minus an unclaimable B. **Not a finding.**

**4. Indigo `observed_at` approximation drift.** `oracle/indigo.ak:96-118` already analyses both directions (lookahead increase → stricter; lookahead decrease → permissive but not exploitable because `tx_upper <= valid_until` uses the exact datum value). Re-walked the analysis with Aegis's freshness gates `tx_lower >= observed_at && tx_lower <= valid_until && tx_upper <= valid_until` (policy.ak:199). Confirmed: even if Indigo halves the lookahead so our `observed_at` lands earlier than reality, the `tx_upper <= valid_until` check uses the EXACT datum.expiration, which is the binding freshness gate. The `tx_lower >= observed_at` widening only permits txs to claim with an earlier `tx_lower`, but the reference input still has to exist at tx-inclusion time, and the price in the reference input is the published value. No replay surface beyond what Aiken already accepts for any reference-input-driven validator. **Not a finding.**

**5. Cross-validator `>=` vs `==` (R7-C).** `policy.ak:401` (Cancel) checks pool output `>=`; `pool.ak:1264` (AcceptCancellation) enforces `==`. Both validators run in the same tx (Cancel + AcceptCancellation are co-spent). The `==` is the binding leg; `>=` is permissive. No exploit. **Confirmed INFO.**

**6. Treasury donation field 22 zero-set with malformed redeemer.** `Underwrite { coverage, premium }` derives `required_donation = calculate_treasury_cut(premium, 200, 2_500)`. The check at `pool.ak:748-752` requires `Some(amt) → amt >= required_donation`. There is no way to "set donation field to None" while having `required_donation > 0` — the `None` branch requires `required_donation == 0`. The only way to make `required_donation == 0` is `premium <= 50` lovelace (since `200 / 10_000 × 2_500 / 10_000 = 5e-5` ratio, and Aiken's two-stage floor takes `1 × 200 / 10_000 = 0 × 2_500 / 10_000 = 0`). Premium <= 50 lovelace fails `is_above_minimum(2_000_000)`. **Not a finding.**

**7. Reference-script substitution via hash collision.** BLAKE2b-256 is the underlying hash; reference-script identity is the hash of the script, so an attacker would need a 256-bit preimage collision. Not computationally feasible. I also scanned for places where a script is referenced by NAME rather than hash — none. **Not a finding.**

**8. Datum schema drift V11 → V12 → V12.2.** Old V11 PolicyDatum has 10 fields; V12+ has 12 (added `partner_address` + `partner_share_bps`). Aiken's `expect pdat: PolicyDatum = raw_pdat` is a positional Constr_0 decode that fails on field-count mismatch — V11 datums fail to decode under V12.2 validators, exactly as documented at `types.ak:97-104`. No bypass surface. The V11 validator hash is still on chain at its own hash (different param set), so V11 policies are still claimable via the V11 validator — but that's a separate-on-chain-protocol concern, not a V12.2 drain. **Not a finding.**

**9. `floor_to_min_utxo` dead helper.** Filed as R8-OBS-1 above. INFO, not security.

**10. ECON-1 (BatchClaim same-insured cross-policy).** Per R6 + R7: attacker short-changes themselves (1× tx_fee cost for 1× payout vs N separate Claim txs that each pay their own payout). Not a drain. Deferred to v12.3 per spec. **Not a new finding.**

**11. Pool NFT one-shot mint.** `pool_nft.ak:47-91`: requires `init_utxo_consumed && named_qty == 1 && total_under_policy == 1`. Burn path is `total < 0`. Multi-asset-name-under-policy attack rejected by `total_under_policy == 1`. **Confirmed sound.**

**12. LP token mint direction/quantity.** `lp_token.ak:42-65` + `pool.ak:878-880` (AddLiquidity LP mint exact-match against `lp_supply` delta) + `pool.ak:902-905` (RemoveLiquidity burn exact-match). The pool's `value_ok` + `datum_ok` form a closed system. **Confirmed sound.**

**13. AegisSelf publisher-key compromise.** Two-layer pin (NFT under one-shot policy + publisher VKH) at `oracle/aegis_self.ak:55-66`. Compromise of the publisher key alone does not unlock new fake oracle UTxOs because the one-shot mint init UTxO is already spent; compromise of the one-shot mint policy alone is impossible without the consumed init UTxO. **Confirmed sound.**

**14. Indigo NFT script-credential pin.** Three-layer handshake at `oracle/indigo.ak:217-253` (NFT-canonical-membership + per-iAsset script credential via paired list + single-token-of-policy). Walker correctness verified by the existing `indigo_pair_resolve_*` tests. **Confirmed sound.**

## Recommendation

**Block mainnet on R8-DRAIN-1 fix.** This is not a pool-drain finding, but it IS a structural team-revenue capture that:
1. Scales linearly with premium (a single 100 000-ADA Underwrite diverts 400 ADA from team to attacker change).
2. Is invisible to off-chain analytics (the policy datum still records `partner_address = team_address`, so revenue accounting looks correct on a casual read).
3. Has a one-line fix in three branches with three regression tests. ETA ~2 hours including aiken check + redeploy.

The fix should land before mainnet because:
- Mainnet `min_premium = 100 ADA` means small-premium attackers are gated by tx-fee economics, but large-premium ones are not (and large-premium policies are the Draper Dragon target use case).
- Auditor handoff is structurally clean otherwise; adding a one-predicate fix doesn't delay the audit.

R8-OBS-1 (dead helper) can ride along in the same redeploy or be deferred to v12.3 cleanup.
