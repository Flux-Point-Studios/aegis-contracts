## 1. What this is (and what it isn't)

We built an **Aegis-specific** symbolic executor on top of Z3. It hand-encodes
the actual `&&`-chain a chosen Aiken validator branch enforces, lifts each
`let foo_ok = ...` line to a NAMED Z3 guard, and proves safety properties as
**negated claims fed to Z3** (SAT = counterexample, UNSAT = proven across the
full symbolic input domain).

This is **NOT**:

- A general Plutus FV framework. We do not model UPLC, CBOR, the script-cost
  model, or arbitrary Aiken programs.
- A full ScriptContext model. We encode only the fields each branch actually
  reads, and document the omissions in `context.py` (see §5 below).

The Round-9 fee-math Z3 work (`z3_conservation_proof.py`) proved
invariants on the **arithmetic** in isolation. This pass elevates the
work to **branch level**: the validator's full guard chain is encoded,
so a property like "pool conservation" now confirms the validator
actually reads `premium` from the same source the math assumes.

## 3. Design decisions (and the rationale)

### 3.1 Symbolic representation: flat Z3 Int dataclasses

`PolicyDatum`/`PoolDatum`/etc. become Python dataclasses of Z3 `Int`s.
We do NOT encode CBOR — we encode LOGICAL fields. ByteArrays become
opaque Z3 Ints whose only meaningful operation is equality. This is
load-bearing for two reasons:

1. The Aegis validator only ever compares ByteArrays for equality
   (`new_datum.pool_nft == datum.pool_nft`); it does NOT inspect their
   bytes. So Int-identity is observationally indistinguishable.
2. CBOR-related properties (canonical-form round-tripping etc.) are
   out of scope for branch-level safety FV. They live in
   `reference_aegis_v8_cbor_canonical` in the memory bank.

If a future branch needs byte-string properties (e.g. prefix-match for
Orcfax feed IDs), refactor the corresponding field to a Z3 `String` or
`SeqRef`. The dataclass is the migration point.

### 3.2 List representation: the encoder lifts list-walks to their result

Plutus validators take `inputs: List<Input>` and `outputs: List<Output>`.
Rather than model lists symbolically (bounded length + Z3 Array sort)
we lift each `list.find` / `list.any` / `list.foldl` call to its
**result**. Example:

```aiken
let team_output_funded =
  output_to_address_at_least(outputs, team_address, team_cut)
```

becomes, in the encoder:

```python
ctx.team_output_lovelace >= inter.team_cut
```

where `ctx.team_output_lovelace` is "the max lovelace at any output at
`team_address`, or 0 if no such output exists." This is exactly the
semantic the validator cares about — and it avoids the combinatorial
explosion of modelling the full list.

**Trade-off**: properties that depend on multi-output topology (e.g.
"team and partner outputs are DISTINCT outputs in the list") are
**not directly expressible**. The R8-DRAIN-1 property dodges this by
working at the Address-equality level (which IS expressible) — the
combinatorial topology is the OFF-CHAIN concern; the on-chain
validator only enforces that some output exists at each address. If a
future branch needs topology-level reasoning (e.g. BatchUnderwrite's
N policy outputs), extend `SymbolicScriptContext` with a bounded
Z3 Array of outputs and a per-index NFT/value/datum projection.

### 3.3 Named guards + `disable_guards` for load-bearing proofs

Every `let foo_ok = ...` in the Aiken source maps to one entry in
`UnderwriteEncoder._guard_constraints()`. The encoder's `encode(ctx)`
returns the conjunction unless the caller passes
`disable_guards={"foo_ok"}` — in which case THAT specific guard is
dropped, and we expect Z3 to find a counterexample.

This is the **load-bearing-guard PROOF** mechanism. Two patterns:

- `test_property_X_proven_on_underwrite()` — full encoder + property.
  UNSAT = proven.
- `test_property_X_finds_counterexample_when_guard_Y_disabled()` —
  drop guard Y; expect SAT. If you get UNSAT, **guard Y is redundant
  for property X** — surface as a finding.

Pristine-and-flawless point: typos in `disable_guards` raise
`ValueError`. Silent drops of nonexistent guards would let an
auditor's proof go through accidentally.

### 3.4 Properties return the NEGATION (Z3 finds counterexamples)

A property's `check(encoder, ctx)` returns a Z3 expression that is
**SAT iff the property is violated**. This convention matches the
counterexample-driven workflow and avoids needing two methods.

The test rubric (per the spec) is:

```python
def test_property_X_proven_on_underwrite():
    ctx = fresh_underwrite_context()
    encoder = UnderwriteEncoder()
    solver = Solver()
    for c in encoder.encode(ctx): solver.add(c)
    for c in pin_protocol_constants(ctx): solver.add(c)
    solver.add(PropertyX().check(encoder, ctx))
    assert solver.check() == unsat
```

### 3.5 Inductive invariants

The `no_negative_active_coverage` property is INDUCTIVE: it claims
"IF the pre-state is solvent, THEN Underwrite preserves solvency."
The pre-condition explicitly states `0 <= old_active <= old_total`
AND `old_pool.protocol_fee_bps == consts.protocol_fee_bps`.

Why the second clause? At small premiums and degenerate fee_bps, the
floor-pad pushes `fee_total > premium`, making `net_pool_growth < 0`.
The pool LOSES lovelace on those txs (V12.2 spec §10.1 says the LP
absorbs this cost — it's intentional). For the inductive invariant to
hold, the pre-state must use the canonical fee_bps; the off-chain
init-pool tx is the base-case oracle.

**FUTURE WORK** (for the next agent): an UNCONDITIONAL proof requires
verifying every branch (`ProcessClaim`, `BatchUnderwrite`,
`AddLiquidity`, `RemoveLiquidity`, `AcceptCancellation`,
`BatchExpireProcess`) preserves the same invariant. That's the
cross-branch composition step, naturally enabled once all six branch
encoders exist.

## 4. Differential testing methodology

The encoder is hand-derived from `pool.ak`. The trust handshake
between encoder and chain is the JSON fixture layer:

`tests/fixtures/underwrite_positive.json` is a known-good scenario
(500 ADA premium, 5000 ADA coverage, solo policy, pool starts at 100k
ADA / 10k ADA committed) whose arithmetic was hand-computed against
the Hybrid Fee math (see `tests/test_encoder_underwrite.py::
test_intermediates_pin_fee_total_on_positive_fixture`):

- `raw_fee = 500e6 * 200 / 1e4 = 10_000_000` (10 ADA)
- `fee_total = max(2e6, 10e6) = 10_000_000`
- `net_pool_growth = 500e6 - 10e6 = 490_000_000`
- `treasury_cut = 500e6 * 200 / 1e4 * 2500 / 1e4 = 2_500_000`
- `team_cut = 10e6` (partner is None → silent solo)

The differential test pins every Z3 variable to the fixture's
concrete value, adds the encoder's constraints, and asserts the
solver is SAT (= encoder accepts).

Each negative fixture violates EXACTLY ONE guard and names it in
`_violates`. The test pair is:

1. With the full encoder: assert UNSAT (= encoder rejects).
2. With ONLY that guard disabled: assert SAT (= encoder would accept
   if not for that guard). This is the load-bearing proof at the
   fixture layer.

**Three negative fixtures shipped**, covering three of the most
audit-relevant exploits:

| Fixture                                              | Guard violated         | Real-world reference |
|------------------------------------------------------|------------------------|----------------------|
| `underwrite_negative_A024_negative_coverage.json`   | `coverage_positive`   | A-024 live exploit (`01a1067c...`) |
| `underwrite_negative_R8DRAIN1_partner_aliased.json` | `partner_not_aliased` | R8-DRAIN-1 (round-8 red-team) |
| `underwrite_negative_mutated_lp_policy.json`        | `immutable_ok`        | R8-DRAIN-1 family |

**NOT YET DONE** (FUTURE WORK for the next agent): run the actual
Aiken validator on the same scenarios via `aiken check` with a
test-helper that decodes our fixture into Aiken expressions and
asserts the validator accepts/rejects to match. The current
methodology RELIES on the hand-verification of the fixtures. A
mechanical Aiken-vs-Z3 differential is the strongest possible trust
handshake; it's deferred for now because the Aiken test scaffolding
requires `cmd //c "aiken ... 2>&1 > file"` (Windows bash stdout drop —
see memory bank `reference_aiken_windows_stdout_workaround`) and the
JSON-to-Aiken-decoder is ~300 LOC of plumbing.

## 5. Modelled fields (and explicit omissions)

### 5.1 What the SymbolicScriptContext encodes

For the Underwrite branch:

- **Old PoolDatum** — all 6 fields (total_liquidity, active_coverage,
  lp_token_policy, protocol_fee_bps, pool_nft, lp_supply).
- **New (continuation) PoolDatum** — all 6 fields.
- **New PolicyDatum** (on the policy output) — all 14 fields, incl.
  V12 partner fields.
- **Underwrite redeemer** — coverage + premium.
- **own_input_lovelace + cont_output_lovelace** — the pool value
  projections the validator inspects.
- **team_output_lovelace, partner_output_lovelace** — the lifted
  results of the `output_to_address_at_least` walks.
- **own_pool_script_hash** — the script credential of the consumed
  pool input (for the policy-pool-binding check).
- **validity_range (lb, ub)** — POSIX-ms bounds.
- **treasury_donation (is_some, amount)** — Option<Int>.
- **Compile-time constants** (team_address, pool_address,
  policy_script_hash, min_utxo, min_premium, partner_share_cap,
  treasury_share, protocol_fee_bps). Modelled as Z3 Ints + a
  `pin_protocol_constants` helper that fixes them to preprod values.

### 5.2 NOT modelled (load-bearing omissions)

| Omission | Why deferred | Branch impact if extended |
|----------|--------------|---------------------------|
| Full `inputs`/`outputs` lists | Lifted to result of list-walks (§3.2). | BatchUnderwrite needs a bounded list array indexed by Z3 Int — the natural extension point. |
| `Value`/`Asset` maps | We model only lovelace projections + NFT-presence booleans. | If a future branch checks token-quantity invariants (e.g. LP token mint = exact `calculate_lp_mint`), extend `SymbolicValue` with a bounded asset-map. |
| Mint / withdrawal / cert lists | Underwrite ignores. | AddLiquidity / RemoveLiquidity will need `mint` (for LP token mint/burn quantity). |
| Other-script redeemers | Cross-script binding is via the policy output's `pool_nft` check, which we DO model. | The policy-validator branch is a separate encoder; symbolic-executor v0.2 wires policy + pool together. |
| Witnesses / extra_signatories | Pool validator ignores. | Cancel (policy) reads `extra_signatories`; ship when porting the policy validator. |
| CBOR encoding | Out of scope — see `reference_aegis_v8_cbor_canonical`. | Never. CBOR FV is a separate workstream. |
| `Address` stake-credential vs payment-credential split | We treat partner_address as a single Int. | Tighten to two Ints (payment + stake) if a future property needs them to differ. Current model conservatively rejects an alias that the validator would also reject. |
| Recursive/inductive proofs across branches | Each branch is encoded in isolation. | Future cross-branch composition step — see §3.5. |

## 6. How to extend to a new branch (checklist)

For the next agent adding e.g. `ProcessClaimEncoder`:

1. **Read the Aiken source.** Identify every `let foo_ok = ...` and
   every `expect Some(X)` / `expect Pattern = expr`. Each becomes a
   named guard.
2. **Reuse `SymbolicScriptContext`.** ProcessClaim consumes a policy
   input — extend the context (or build a `SymbolicProcessClaimContext`)
   with a `SymbolicPolicyDatum` for the CONSUMED policy plus the new
   redeemer.
3. **Write the encoder.** Mirror `UnderwriteEncoder`:
   - `GUARD_NAMES` tuple (ordered as the Aiken `&&`).
   - `_intermediate_definitions(ctx)` for derived quantities (e.g.
     for ProcessClaim, the oracle price freshness binding).
   - `_guard_constraints(ctx)` returning `GuardedConstraints` per guard.
4. **Wire it into `cli.py`.** Add to `BRANCHES`.
5. **Add fixtures.** Build the positive-path JSON + at least two
   negative fixtures covering known exploits.
6. **Add tests.** Per the rubric:
   - `test_encoder_lists_all_expected_guards`
   - `test_encoder_disable_unknown_guard_raises`
   - `test_encoder_accepts_positive_fixture`
   - `test_encoder_rejects_each_negative_fixture`
   - `test_disabling_violated_guard_recovers_acceptance`
7. **Add properties.** ProcessClaim's safety properties candidates:
   - `payout_in_bounds`: `0 < payout <= old_active_coverage`
   - `claim_oracle_fresh`: `validity_range.ub - oracle.created_at <= freshness_window`
   - `claim_below_strike`: `oracle_price < policy.strike_price` (the claim is justified)
   - `immutable_pool_datum`: same as Underwrite — share the property.
   - `pool_value_decreases_by_payout`: `cont_output.lovelace ==
     own_input.lovelace - payout`.
8. **For EACH property, write the test pair.** PROVEN UNSAT under the
   full encoder; SAT when the load-bearing guard is disabled.

## 7. How to add a new property (checklist)

1. Subclass `BaseProperty`. Set `name` and `description`.
2. Implement `check(encoder, ctx) -> BoolRef` that returns the
   NEGATION of the safety claim.
3. Add a unit test `test_property_<name>.py` with at least two tests:
   - `test_<name>_proven_on_<branch>()` (UNSAT).
   - `test_<name>_finds_counterexample_when_<guard>_disabled()` (SAT).
4. Register the property in `cli.py::PROPERTIES`.
5. Run `python -m symbolic_executor verify --branch <X> --property <name>`
   and confirm `PROVEN` prints.

## 9. Known limitations + honest scope statement

- **Single-branch.** Only Underwrite is encoded. ProcessClaim,
  BatchUnderwrite, AddLiquidity, RemoveLiquidity, AcceptCancellation,
  BatchExpireProcess are FUTURE WORK. The framework is designed to
  accept them following §6's template.
- **No mechanical Aiken-vs-Z3 differential yet.** The fixture
  positive/negative status was hand-verified. A pytest plugin that
  invokes `aiken check` on a generated harness for each fixture is
  the strongest possible trust handshake; it's the natural next step.
- **No cross-branch composition.** A property holding on every
  individual branch doesn't trivially compose to "holds across any
  transaction sequence." The cross-branch step (an inductive
  invariant over the validator-hash lifecycle) needs the full six
  branch encoders first.
- **List topology is summarized to projections.** Properties that
  depend on the exact list of outputs (e.g. "team and partner
  outputs are different UTxOs") cannot be directly expressed. Aegis's
  Underwrite branch doesn't need topology — the
  `partner_address_not_aliased` guard makes the Address-equality
  level sufficient.
- **CBOR-encoding properties are out of scope.** See
  `reference_aegis_v8_cbor_canonical` (memory bank) for the CBOR
  invariants we DO check, via a separate Python test layer.
- **Z3 timeout / unknown handling.** All current invariants resolve
  in milliseconds. A future branch with non-linear arithmetic
  (e.g. ProcessClaim's price * coverage computation) may time out;
  add `solver.set("timeout", N)` and surface UNKNOWN as a finding.
