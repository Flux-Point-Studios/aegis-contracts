## 3. Scope markers (load-bearing honest disclosures)

### S1. BatchUnderwrite `no_negative_pool_state` pre-condition

The validator (V12.2 §10.1) INTENTIONALLY allows the LP to absorb
the aggregate min-utxo floor cost on small-premium batches. A batch
of 100 policies each at 2 ADA premium has `total_premium = 200 ADA`
and `fee_total_sum = 100 × 2 ADA = 200 ADA`, so `net_pool_growth =
0`. A batch of 100 policies each at 1.999 ADA premium would yield
`fee_total_sum > total_premium`, meaning the pool's lovelace SHRINKS
on the tx — the LPs absorb the difference in exchange for a
linear-in-premium user-facing fee curve.

For the `no_negative_pool_state` property to be PROVEN on
BatchUnderwrite, we add the pre-condition

```
old_total + total_premium >= fee_total_sum
```

This is the "LP cushion" — the pool must carry enough lovelace to
absorb the worst-case aggregate floor cost. The chain bootstrap
(100 ADA init-pool) provides the base case. The property is
PROVEN UNSAT under this pre-condition. Without the pre-condition,
the property is NOT a safety claim — it's a violated invariant by
design.

Cross-reference: the foundation's `no_negative_active_coverage`
takes the same shape — it adds `protocol_fee_bps == 200` as an
inductive pre-condition because the validator reads fee_bps from
the datum and degenerate values would make Underwrite drain the
pool by design.

### S2. BatchUnderwrite list-walk lifting

Per the foundation's scope statement (§3.2), Plutus list-walks are
LIFTED to scalar aggregates. For BatchUnderwrite this means:

- `batch_policies_match_totals_v12` produces a record of aggregate
  sums (`cov_sum`, `prem_sum`, `fee_total_sum`, `team_total`,
  `partner_totals_sum`) plus aggregate flags (`funded_ok`,
  `shares_ok`, `partner_outputs_all_funded`,
  `aliased_partner_present`).
- The encoder's guards check the FLAGS, not individual policies.
- The R8-DRAIN-1 batch arm is modelled as
  `aliased_partner_present == 0`; the validator's `list.all`
  iteration over `partner_totals` is condensed to a single 0/1
  indicator.

Properties expressible:
- "EVERY policy's partner_share <= cap" — yes, via `shares_ok`.
- "the aggregate team output is funded against team_total" — yes.
- "every partner output is funded" — yes, via
  `partner_outputs_all_funded`.

Properties NOT directly expressible:
- "policy at index k of the batch has a specific datum value" —
  requires per-element list modelling.
- "two policies in the batch share a coverage_amount" — requires
  pairwise list reasoning.

**Future extension point**: replace `SymbolicBatchFeeTotals` with a
bounded Z3 `Array[Int, SymbolicPolicyEntry]` indexed by policy
position. The natural step once Aegis ships a property that
explicitly depends on list topology (e.g. "no two policies in the
same batch can be perfect duplicates"). For V12.2 R7 no such
property has surfaced.

### S3. AcceptCancellation negative-`premium_paid` corner case

The Z3 model's signed-integer division (Euclidean: floor toward
negative infinity) makes the math identity
`refund_amount = premium_paid * 9_000 / 10_000` produce a
`refund_amount` numerically GREATER THAN `premium_paid` when
`premium_paid < 0`. Concretely, at `premium_paid = -1`,
`cancellation_fee = -1`, `refund = -1 - (-1) = 0`, and `0 > -1`
trivially.

This is NOT a vulnerability — the validator's `bounds_ok` guard
enforces `refund_amount >= 0`, so no lovelace flows OUT of the pool
to the insured at a negative-premium policy (the refund of 0 means
the insured receives nothing). Aegis on-chain policies are only
created via `Underwrite`, which enforces `premium > 0`, so the
corner case is unreachable on chain. The Z3 layer needs an explicit
`premium_paid >= 0` pre-condition for the property to be PROVEN —
captured in `properties/refund_bounded_by_premium.py`.

## 4. Redundant-guard findings

The framework's load-bearing-guard test mechanism surfaced three
genuine redundancies. These are NOT vulnerabilities — they are
defense-in-depth observations: the validator carries explicit
guards that the encoder's other constraints (or another guard)
already enforce.

### R1. ProcessClaim — `remains_non_negative` is redundant against `datum_ok`

`pool.ak::ProcessClaim` line 870 carries an explicit
`remains_non_negative = new.total >= 0 AND new.active >= 0` guard.
The preceding `datum_ok` guard calls `verify_claim_datum`
(`lib/aegis/pool.ak::120`), which already enforces:
- `payout >= 0`
- `payout <= old_active`
- `new_total >= 0`
- `new_active >= 0`

Z3 confirms that disabling ONLY `remains_non_negative` (leaving
`datum_ok` enabled) keeps the `no_negative_pool_state` property
PROVEN. The validator's explicit guard is defense-in-depth — it
remains useful as a future-proofing layer in case
`verify_claim_datum` is ever refactored to drop the
non-negativity checks.

### R2. AcceptCancellation — `bounds_ok` is redundant for `no_negative_pool_state`

`pool.ak::AcceptCancellation` line 1309 carries `bounds_ok =
refund >= 0 AND refund <= datum.total_liquidity AND
policy_datum.coverage_amount <= datum.active_coverage`. The
`remains_non_negative` guard (line 1332) is what actually
load-bears the post-state non-negativity. Z3 confirms dropping
`bounds_ok` while keeping `remains_non_negative` still PROVES the
property.

The `bounds_ok` guard's `refund <= old_total` and `coverage <=
old_active` clauses ARE load-bearing for OTHER properties (they
bound the pool's outflow from below, which matters for any future
"pool doesn't underflow on a single tx" property). But for the
specific `no_negative_pool_state` post-condition, the inductive
pre-state + `datum_ok` + `remains_non_negative` chain suffices.

### R3. AcceptCancellation — `refund_bounded_by_premium` is math-only

The encoder's intermediate definition
```
refund_amount = premium_paid - (premium_paid * 1_000 / 10_000)
              = premium_paid * 9_000 / 10_000
```
structurally guarantees `refund_amount <= premium_paid` for any
non-negative premium. No guard load-bears this claim — it's purely
a property of the formula. Dropping the `bounds_ok` guard (the
only guard that bounds `refund_amount` explicitly) leaves the
property PROVEN.

This is the moral analogue of the foundation's `pool_conservation`
finding: the safety claim is a math identity baked into the encoder
definitions, NOT into the `&&` chain.

## 9. Architecture changes

### 9.1 Per-branch contexts

Each branch's needed fields differ — ProcessClaim consumes a
policy (no new policy datum); AddLiquidity needs `mint_lp_qty`;
BatchUnderwrite needs the lifted `SymbolicBatchFeeTotals` record.
Rather than extending the foundation's `SymbolicScriptContext`
with optional fields (which would couple the foundation tests to
their evolution), we introduced five per-branch context
dataclasses sharing the SAME naming conventions for fields they
have in common (`old_pool_datum`, `consts`, etc.). Properties
that read these common fields work across branches with no
refactor.

### 9.2 Branch-parameterized properties

The `PoolConservationProperty`, `ImmutablePoolDatumProperty`, and
`PartnerNotAliasedProperty` now accept a `branch` constructor
argument. They dispatch on this string:

- `pool_conservation` — different pool-delta formulas per branch.
- `immutable_pool_datum` — lp_supply is mutable on AL/RL, immutable
  elsewhere.
- `partner_not_aliased` — Underwrite reads `new_policy_datum`; AC
  reads `consumed_policy_datum`; BatchUnderwrite reads the
  aggregate flag.

The default `branch="Underwrite"` preserves the foundation tests'
behaviour exactly (zero refactor of the foundation tests).

### 9.3 CLI dispatch

`cli.py` introduces `BRANCH_ENCODERS`, `BRANCH_CONTEXT_FACTORIES`,
and `BRANCH_PROPERTIES`. The last is a nested map `branch ->
{property_name -> property_factory}`. The CLI uses it to gate
which (branch × property) pairs are verifiable and to construct
the correctly-parameterized property instance.

`verify-all --branch ALL` is new — iterates every (branch,
property) pair across the registry. Useful for CI.

## 10. Updated future-work list

What this extension pass DID:
- All five remaining `pool.ak` branches encoded.
- All universal + branch-specific properties PROVEN.
- Branch-parameterized property infrastructure.
- CLI dispatch over branches.

What's STILL future-work (carried forward from the foundation
report's §9):

1. **Mechanical Aiken-vs-Z3 differential.** Still hand-verified.
   A pytest plugin that invokes `aiken check` with a
   JSON-to-Aiken decoder on the fixtures would be the strongest
   possible trust handshake. ~300 LOC of plumbing — deferred
   because the Windows `aiken` stdout-drop workaround (see
   `reference_aiken_windows_stdout_workaround`) adds friction.

2. **Cross-branch composition.** Each branch encoder is in
   isolation. A property like "no Aegis lifecycle drains the
   pool to zero" requires composing the six branch encoders into
   an inductive invariant over the validator-hash lifecycle. The
   six encoders now exist, so this is the natural next step.

3. **`BatchExpireProcess`.** Not in the user's five-branch list.
   The redeemer is simple (`total_returned` + a single datum
   transition); ~50 LOC encoder + 3 properties. Skipped here to
   stay within the requested scope.

4. **Per-element list topology.** As scope-marked at S2, the
   walker output is lifted to scalars. A future R8-DRAIN-2-like
   finding that depended on the EXACT list order of partner
   outputs would require list-array modelling. None has
   surfaced.

5. **Mainnet vs preprod constant pinning.** `pin_protocol_constants`
   pins to preprod (`min_premium == 2 ADA`). A mainnet pin
   variant (`min_premium == 100 ADA`) would let the property
   checker prove the same invariants under the mainnet constants
   AND surface any preprod-only assumptions baked into a guard.

6. **Z3 timeout / unknown handling.** All current invariants
   resolve in milliseconds (max ~30 ms for
   `BatchUnderwrite.no_negative_pool_state`). A future property
   with deeper non-linear arithmetic could time out; the CLI
   would surface UNKNOWN as a finding.

7. **Policy validator encoder.** Aegis's two validators are
   `validators/pool.ak` (covered here + foundation) and
   `validators/policy.ak` (the per-policy state machine: Claim,
   Cancel, Expire). Adding a `policy_*` encoder family would let
   us prove cross-validator invariants like "no Claim tx accepted
   by `policy` is rejected by the corresponding pool-side
   `ProcessClaim`".
