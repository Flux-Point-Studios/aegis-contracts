# Aegis V12.2 Round 9: Cardano Audit Landscape Research (2025-2026)

**Search date:** 2026-05-20. Word count ~3,200.

## Problem framing

You've already exhausted the high-value internal red-team surface: 8 rounds of adversarial review, Z3 conservation-law proofs on fee math, mutation testing on `pool.ak`, and a live preprod deployment at V12.2 + R7 + R8. The question is which of three residuals — **whole-validator formal verification**, **MEV/ordering analysis**, **specialized cryptographer review** — to invest in pre-audit vs. delegate to the auditor. The TVL target ($20-50k initial) constrains how much can rationally be spent on belt-and-braces work.

## Q1 — Cardano formal-verification toolchain (2025-2026)

### 1.1 IOG SmartCodeVerifier (the headline development)

The single biggest shift since 2024 is **IOG's SmartCodeVerifier**, announced July 2025 in the IOG blog post "A new era of smart contract verification on Cardano" ([iog.io blog 2025-07-17](https://www.iog.io/blog/posts/2025/07/17/a-new-era-of-smart-contract-verification-on-cardano/)). Repo: [github.com/input-output-hk/smartcode-verifier](https://github.com/input-output-hk/smartcode-verifier).

Architecture: a five-step pipeline that transpiles surface-language source (**Plinth, Aiken, Plu-ts, UPLC, Opshin** all listed as targets) → Lean4 intermediate representation → SMT queries → Z3/CVC5 → returns "replayable proofs, counterexamples, or manual proof obligations." The design goal explicitly is *no Lean4 expertise required from the developer*; the user writes properties in a "Universal Annotation Language."

**Current state (as of search date):** Active development; only 13 commits on the main repo; the README states "the following description is a bit outdated" and that active development has moved to sister repos `Lean-blaster`, `PlutusCore Blaster`, `CardanoLedgerAPIBlaster`. **Zero published releases.** Not usable for a real audit pipeline yet. IOG's Q3 2025 progress report ([iog.io news](https://www.iog.io/news/strengthening-cardanos-foundations-q3-2025-progress-report)) describes ongoing Plinth-first work with Aiken support planned later.

**Verdict for Aegis:** Not actionable in the May 2026 mainnet window. Worth watching for V13. Cite it in the audit-readiness package as "we are aligned with the direction IOG is taking on FV" but do not gate the audit on it.

### 1.2 K-Framework Plutus Core semantics (Runtime Verification)

Repo: [github.com/runtimeverification/plutus-core-semantics](https://github.com/runtimeverification/plutus-core-semantics). KPlutus is described as "approaching alpha" in issue #152, with benchmarks showing `kplc` is faster than `uplc` on some computational tasks. RV's main page ([kframework.org/projects](https://kframework.org/projects/)) lists Plutus as one of many K projects.

**Status assessment:** K is production-grade for KEVM (Ethereum), but the Plutus Core version is alpha-stage and not consumed by audit firms in the way KEVM is. Using K-Framework today on Aegis means hiring RV directly — it is not a tool a non-PhD engineer wields.

### 1.3 Coq / coq-uplc (Anastasia Labs)

Catalyst Fund 12 funded Anastasia Labs to build [github.com/Anastasia-Labs/coq-uplc](https://github.com/Anastasia-Labs/coq-uplc), a Coq encoding of the Cardano CEK machine. Status per repo: 18 commits, "Under construction…" in the README's usage section, **2 of 5 milestones complete** per Catalyst tracker ([projectcatalyst.io/funds/12](https://projectcatalyst.io/funds/12/cardano-open-developers/anastasia-labs-smart-contract-formal-verification-framework)). No usable code-examples for non-PhD engineers. This is research-grade.

### 1.4 Aiken-native formal verification

Aiken's official line: "Property-based framework + formal verification, mathematically prove smart contract properties" ([cardanofoundation.org blog](https://cardanofoundation.org/blog/aiken-the-future-of-smart-contracts)). In practice as of v1.1.22 (released around 2026-05-01), what Aiken actually ships is:

- **Property-based testing with shrinking** ([aiken-lang.org/language-tour/tests](https://aiken-lang.org/language-tour/tests))
- Unit testing harness
- No native FV / SMT extraction

There is no Aiken-native "prove this validator is correct" workflow. The closest is using Aikido (see 1.6) or transpiling via the future SmartCodeVerifier.

### 1.5 Tweag cooked-validators

[github.com/tweag/cooked-validators](https://github.com/tweag/cooked-validators) — Haskell library that interacts with any UPLC artifact (Plutus, Plutarch, **Aiken**), purpose-built for "testing, auditing, and behavioral exploration." Tweag uses it in their own audits as step one — write transaction-generating code, then mutate to act as attacker. This is the most production-ready FV-adjacent tool today. Open-source. Documented and used live.

**A non-PhD engineer can use this.** Recommended pre-audit hygiene.

### 1.6 Aikido Security Analysis Platform (the surprise find)

[github.com/Bajuzjefe/Aikido-Security-Analysis-Platform](https://github.com/Bajuzjefe/Aikido-Security-Analysis-Platform) — Aiken-specific platform with **75 detectors** mapped to CWE IDs, plus an SMT verification lane with "Cardano domain axioms (value conservation, signature semantics, minting policy)," plus a `ScriptContext` builder for transaction simulation.

Claims: 85% coverage on TxPipe's Strike Finance audit; deployed against SundaeSwap and Anastasia Labs. 1,186+ tests. Version 0.3.1.

**Caveat:** Single-developer GitHub repo, not yet vetted by the official Cardano security firms. But if the claims hold, this is precisely the "automated property-checker since 2024" that didn't exist when Aegis started. **Strong candidate for Aegis to run pre-audit.** Worst case it produces noise the auditor can dismiss; best case it surfaces something for free.

### 1.7 TLA+

No evidence of TLA+ being used in any published Cardano audit (Liqwid, Indigo, Minswap, SundaeSwap, Lenfi, WingRiders all reviewed below). Cardano's deterministic EUTXO model means concurrent-state-machine modeling is less load-bearing than on EVM. **Skip.**

### 1.8 Synthesis for Q1

| Tool | Aegis-usable today? | Action |
|------|--------------------|--------|
| SmartCodeVerifier | No | Watch for V13 |
| K-Plutus | Only via RV engagement | Bundle into firm choice |
| coq-uplc | No (research) | Skip |
| Aiken native FV | Doesn't exist | n/a |
| cooked-validators | Yes | Optional pre-audit hygiene |
| Aikido | Yes, low cost | **Run it** |
| TLA+ | No precedent | Skip |

**Bottom line:** FV of the whole transition function is genuinely the auditor's domain in 2026. The one cheap pre-audit move is running Aikido against `pool.ak`.

## Q2 — Cardano MEV / ordering analysis

### 2.1 The structural argument

Cardano's marketing is unambiguous: EUTXO + Ouroboros + local determinism = MEV is structurally limited ([iohk.io 2025-05-02](https://iohk.io/blog/posts/2025/05/02/cardano-s-eutxo-model-bringing-deterministic-predictability-to-blockchain/), [ainvest.com](https://www.ainvest.com/news/mev-vulnerabilities-ethereum-cardano-blockchain-security-investment-analysis-2510/)). The technical core: transaction outcomes are determined by inputs at signing time; a block producer cannot reorder and produce a *different* successful outcome the way an Ethereum miner can.

### 2.2 But MEV-equivalent attacks still exist on Cardano

- **Datum-driven races:** Two transactions both wanting to spend the same UTxO. SPO chooses which lands. This is precisely the surface relevant to Aegis: claim races, oracle-refresh races.
- **Concurrency loss** on AMM pools that use shared script UTxOs.
- **Censorship** (SPO can silently drop your tx).

Recent literature: arXiv search returned heavy Ethereum/L2 MEV research in 2024-2026 ([arxiv 2512.17602](https://arxiv.org/pdf/2512.17602), [arxiv 2511.13080](https://arxiv.org/pdf/2511.13080)), but **no empirical Cardano MEV study in the last 24 months**. The Cardano Foundation participated in an Ethereum rollup sandwich paper (mentioned in one search result) but did not publish a Cardano-native equivalent.

### 2.3 Tools available

- **No Flashbots-equivalent dataset for Cardano.** No public mempool aggregator, no MEV-Boost analog, no published "Cardano MEV per epoch" dashboard.
- **Hydra-cluster-as-a-service:** Demeter.run offers "Cardano Hydra Node: self-hosted Hydra node + TUI + dashboard" ([demeter.run/extensions/cardano-hydra](https://demeter.run/extensions/cardano-hydra)). Hydra v1 reached production-ready status October 2025 ([cardano.org news 2025-10-27](https://cardano.org/news/2025-10-27-scaling-cardano-applications-with-hydra/)). This is the closest thing to a "Cardano MEV testbed" — spin up a private head, run adversarial scenarios.
- **Empirical SPO behavior:** The only published empirical Cardano-transaction-graph research is the SSM (shared send mixers) paper ([sciencedirect S2096720924000824](https://www.sciencedirect.com/science/article/pii/S2096720924000824)) — found that 11% of Cardano transactions use SSMs. Not directly MEV but adjacent.

### 2.4 How to set up a Cardano MEV simulation in 2026

1. Spin up a Hydra head via Demeter.run (turnkey, hours not days).
2. Use **cooked-validators** to generate adversarial transaction scenarios.
3. Use **Aiken's property test framework** (with shrinking) to generate stochastic transaction sequences.
4. Run the Aegis validator against the head with multiple "SPOs" applying different ordering policies.

### 2.5 Verdict for Q2

MEV/ordering analysis is **not** worth bringing in-house for Aegis at the $20-50k TVL stage. The relevant attack class for parametric insurance is **claim races** and **oracle-refresh races**, both of which are first-order EUTXO contention issues, not novel MEV. These are already in Aegis's red-team rounds (Round 6/7 covered the BatchClaim arm specifically).

What the auditor should be asked to do: a one-page "adversarial SPO scenarios for Aegis" addendum, not a full MEV review. Most audit firms (MLabs, Anastasia Labs, Invariant0) include this in their default scope.

### 4.1 Findings Aegis should pre-empt (cross-protocol patterns)

- **Burn-arbitrary-iAsset (Indigo V1 critical):** Validators that allow burning more than the user holds via a malformed stability-pool interaction. Aegis equivalent: claim-side payouts that exceed the locked premium pool. Aegis Z3 conservation laws should already cover this — re-confirm in audit prep package.
- **Subtle rounding on withdraw (SundaeSwap):** LP withdrawal undercredits the LP. Aegis LP cancel-cycle has had R7-A min-premium issue already flagged in Round 7; this is the same family. Make sure the auditor sees R7-A.
- **Token uniqueness attacks / faking timestamps (Vacuumlabs Liqwid scope):** Aegis V12.2 uses NFT pins for policy + Charli3 oracle freshness. Re-confirm the freshness window and NFT-only-once invariants are in the audit handoff.
- **Double satisfaction:** Single redeemer authorizing two outputs. Aegis has multi-validator transactions (the bot, the batch claim arm). Auditor should explicitly test this.
- **Locking funds forever:** Validators that have unreachable branches in the redeemer. Mutation testing already covered this on `pool.ak`.

## Q5 — Synthesis recommendation

### 5.1 Which residual to in-house?

| Category | Bring in-house? | Reasoning |
|----------|-----------------|-----------|
| Whole-validator FV | **No** | SmartCodeVerifier isn't shipped. coq-uplc is alpha. The only production path is K-Framework via RV, which is the auditor doing it. Your Z3 conservation-law work already covers the most valuable surface (fee math). Spending more on FV is diminishing returns at $20-50k TVL. |
| MEV / ordering | **No** | Cardano's EUTXO model structurally limits MEV; the relevant subset (claim races, oracle races) is already in Rounds 6-7. Have the auditor sign off on it as a one-page addendum. |
| Cryptographer | **Conditional No** | If Aegis uses standard Ed25519 + CIP-30 + standard CBOR, no crypto novelty exists. The `auth_witness` v8 design has cryptographic flow but you've already done 7 rounds of defense-in-depth on it. Only bring in a cryptographer if the auditor flags a specific question. |

**Cheap pre-audit moves worth doing:**
1. Run **Aikido** against `pool.ak` and the v8 auth validators. Free, single-tool, surfaces CWE-mapped findings.
2. Wire **cooked-validators** into the test harness for the next two weeks. Mutate transactions adversarially.
3. Re-read the **Indigo V1 critical findings** and the **SundaeSwap LP-rounding finding** explicitly against Aegis pool.ak. Document the comparison in the audit handoff.

### 5.2 Audit-firm shortlist (in order of recommended fit)

**1. Anastasia Labs** — best Aiken-native fit, audited the most adjacent protocols to Aegis (Lenfi V2 lending, Minswap V2 AMM, FluidTokens parametric-ish products). The Coq-UPLC framework gives them upside on the FV residual without the RV price tag. **Probable price band: $80-150k for 4-6 weeks**, extrapolating from MLabs Indigo V2.

**2. MLabs** — proven on the most-similar protocol (Indigo V2: CDPs + iAssets + Aiken). $150k / 6w / 4 auditors is the only public price point in the market. Best fit if you want the highest-confidence "we've done this exact shape before" engagement.

**3. Tweag** — strongest if you want lightweight FV bolted on, and you're willing to write transaction-generating code in cooked-validators upfront to accelerate them. Worked on Marlowe (closest protocol to "money-preserving primitives" that Cardano has audited).

**4. Invariant0 (ex-Vacuumlabs)** — best at attack-pattern mining (Liqwid 25-finding report shows depth). Worth a quote even if not the primary.

**5. Runtime Verification** — only if budget is unconstrained. Best at finding *the* subtle bug (SundaeSwap proved this). Slowest, most expensive.

**Skip for Aegis:** Trail of Bits and Least Authority — no Cardano DeFi track record locatable. CertiK — appears in WingRiders and Minswap LBE V2 but the WingRiders 5-Informational report suggests light-touch coverage; not your match.

**Recommended approach:** Send a 1-page audit brief to **Anastasia Labs, MLabs, and Invariant0** simultaneously this week. Compare scope + price + start date. Expect $80-150k and 5-7 weeks elapsed. Budget another 2 weeks for remediation review.

### 5.3 Findings to put in the auditor's "please specifically test" addendum

1. **Burn-arbitrary on claim** — the Aegis equivalent of Indigo V1's critical. Show your Z3 proofs covering this.
2. **LP-rounding on cancel-cycle** — explicit pointer to R7-A.
3. **Double-satisfaction across multi-validator BatchClaim** — pointer to R7-B.
4. **Oracle-freshness race conditions** — the claim path depends on Charli3 + self-published feeds. Explicitly request the auditor walk a multi-oracle-source race.
5. **Validator hash cycles** — your memory already flags "validator const cycles deadlock deploy"; surface this as a design choice, not a vulnerability, but get auditor sign-off.

### 5.4 What the audit *won't* cover (your residual risk after audit)

- Off-chain `policies.py` / build endpoints (only on-chain code is in scope by default; specifically ask for off-chain coverage if you want it — Vacuumlabs/Liqwid scope explicitly excluded off-chain).
- The Shamir 2-of-3 auto-claim wallet — this is operational security, not validator security. Audit it separately or accept the risk for $20-50k TVL.
- Charli3 / Orcfax / self-publish oracle correctness — out of scope for the smart-contract auditor; that's the oracle vendor's problem.
