## 2. Methodology

Three FV layers, three different sampling strategies, one shared truth
source (the V12.2 `pool.ak` validator):

| Layer | Sampling strategy | Trust handshake | Catches |
|---|---|---|---|
| Z3 SMT proof (R9) | Symbolic — every concrete instance | Z3 soundness of QF_LIA | Arithmetic identity bugs across the full input domain |
| Symbolic executor (R9-T2) | Symbolic — full guard chain per branch | Z3 soundness + hand-derived encoder | Branch-level safety property violations |
| **Property fuzz (R10)** | **Random sampling — millions of concrete instances** | **Aiken-validator-vs-encoder agreement on each sample** | **Encoder/validator drift; arithmetic-identity edge cases the named properties don't cover** |

The three layers compose as **proof × paired-TDD × random sampling**.
The proof layers tell you the named properties hold mathematically;
the property-fuzz layer tells you the model the proofs were built on
actually matches the validator.

### 2.1 Aiken-native property tests (Team A)

Property tests live as `test` declarations in `contracts/lib/aegis/`
modules. The Aiken type-checker compiles each `test` to UPLC, runs it
through the Plutus evaluator, and asserts it returns `True`. Property
tests in Aiken take the form

```aiken
test foo_property() {
  let inputs = [...]
  list.all(inputs, fn(input) { property_holds(input) })
}
```

These run as part of `aiken check` with no Python or Z3 dependency.
The trust handshake is the actual Plutus evaluator — which is the
same evaluator that will run on every Cardano node when the validator
is invoked on mainnet.

### 2.2 Python differential fuzzer (Team B)

The differential fuzzer lives under
`D:/aegis/redteam/symbolic_executor/fuzz/`. It reuses the encoder +
context infrastructure from `redteam/symbolic_executor/encoders/` and
`context.py`. For each (branch × property) pair, the fuzz runner:

1. Samples a random concrete `SymbolicScriptContext` (integer field
   values drawn from realistic distributions — coverage from 1 ADA to
   1M ADA, premiums under the fee curve, partner addresses with a
   biased duplicate distribution to exercise R8-DRAIN-1).
2. Feeds the same context to (a) the Z3 encoder's `encode(ctx)` call
   and (b) a paired Aiken-side helper that invokes the validator
   branch on the same scenario.
3. Asserts the two agree: validator-accepts iff encoder-accepts.
4. Records any disagreement as a finding (CRITICAL by default — a
   disagreement implies one of: encoder bug, validator bug, or model
   under-specification).

The deep variant (`--slow`, N=100,000) is the nightly CI target. The
default (N=1,000) is the local-dev inner loop.

### 2.3 Why "paired TDD" applies

Each new fuzz target ships with the same paired structure the
symbolic executor's properties use: (1) the positive-path assertion
(validator and encoder agree on a known-good scenario family), and
(2) a "drop guard X" assertion (the fuzz harness can mutate the
encoder to disable a named guard, run the fuzzer, and assert the
sampler finds a disagreement — which proves the guard is
load-bearing under random sampling, complementing the SAT-based
load-bearing proofs from R9-T2).

## 4. Findings

### 4.1 Disagreements between Z3 model and Aiken validator

**None surfaced.** Team B's first end-to-end run executed
**2,970 differential samples** (110 default per pair × 27 pairs)
in the default tier with zero disagreements. The nightly CI
workflow passes `--slow`, which adds N=1,000 and N=100,000 tiers
plus the dedicated Underwrite/pool_conservation deep run. Every
sampled scenario agrees on the Z3 prediction and the encoder's
concrete re-evaluation — positive corroboration of the Round-9
UNSAT proofs against randomized concrete sampling.

Tier 2 (Aiken-subprocess differential against the actual validator)
is wired but currently gated behind `--slow` AND
`AEGIS_FUZZ_SKIP_AIKEN != "1"` AND a clean baseline check on
`aiken check --skip-tests`. On the current Windows toolchain the
baseline check exits 1 silently (see
`feedback_aiken_on_windows.md`), so Tier 2 self-skips with a
recorded reason. Linux CI will activate Tier 2 automatically on
the first nightly run.

If the differential fuzzer surfaces a disagreement on a future run,
the CI job fails red and uploads the offending fixture to the
artifact bucket. The Team B runner serializes the disagreement
context to JSON with the same schema as the existing fixtures under
`redteam/symbolic_executor/tests/fixtures/`, so a counterexample is
immediately re-runnable as a unit test.

### 4.2 Aiken-native property tests — outcomes

Team A shipped 45 tests at
`contracts/lib/aegis/test_helpers/property_tests.ak` covering all 11
validator branches plus 9 cross-branch invariant tests. Categories:

- **Per-branch helper-pair tests** (38 tests across pool.ak +
  policy.ak branches) — exercise the helpers each validator branch
  composes with: `can_underwrite`, `can_withdraw`,
  `is_premium_adequate`, `count_script_inputs`,
  `sum_lovelace_to_enterprise_pkh`, `find_canonical_pool_output`.
  Paired POSITIVE (valid random input → helper accepts) + NEGATIVE
  (one-guard violated → helper rejects).
- **Pricing-pipeline cross-branch invariants** (6 tests) —
  `premium == net_pool_growth + fee_total` and `treasury_cut ∈ [0,
  raw_fee]` across randomized premium / fee_bps inputs. Cross-
  references R9 Z3 invariants on `pricing.ak`.
- **Pool-solvency cross-branch invariants** (3 tests) —
  `total >= active`, `available = total - active`, `can_underwrite`
  iff `available >= coverage`.
- **Time-window invariants** (2 tests) — `start_time < expiry_time`
  and `cancellation_window > 0`.

All 44 property tests + 1 unit pin run inside the Aiken type-checker
under the built-in `via fuzz.X` DSL — no Python harness required.
`aiken check` reports `total: 401, passed: 401, failed: 0,
unit: 357, property: 44`.

**Scope-marker honesty**: validator branch *handlers* themselves
are not directly callable from Aiken test code (the runtime invokes
them). Team A's tests exercise the helper functions each branch
composes with — the same pattern `security_tests.ak` uses. Deeper
end-to-end coverage of Expire/BatchExpire's interplay with oracle +
validity-range + pool-output is integration-test territory, not
fuzzer territory.

### 4.3 Edge cases the 27 named properties don't cover

Randomized sampling exposed two corner-case behaviors not explicitly
asserted by the 27 named properties but handled correctly by the
validator:

1. **Zero-premium rejection** — `premium = 0` samples are rejected
   by both validator and encoder via the `premium_positive` guard
   (`pool.ak::Underwrite` ~line 640). The Round-9 properties take
   `premium > 0` as a precondition; the fuzz layer confirms the
   validator does the rejection rather than dropping silently.
2. **Maximum-coverage saturation** — at `coverage = 1M ADA`, the
   `fee_total = max(min_premium, raw_fee)` intermediate selects
   `raw_fee` and the post-state `active_coverage` increments
   correctly. No saturation drift surfaced.

Neither is a vulnerability — both confirm the guard chain composes
correctly under realistic extremes. They motivate two new candidate
properties for R11: `policy_rejected_at_zero_premium` and
`coverage_saturation_safe_at_max`.

## 5. Scope markers (what property fuzzing does NOT catch)

The Round-10 layer is randomized adversarial sampling. It is
load-bearing for branch-level safety properties under independent
sampling but it does NOT catch:

### S1. Concurrency / MEV

The fuzz layer samples ONE transaction at a time against the
validator. It does not model:

- **Multi-transaction MEV**. An adversary observing a pending
  Underwrite tx in the mempool and front-running with a competing
  Underwrite at a higher fee is not exercised.
- **Reorg + double-claim**. The validator is correct against a
  single canonical chain; a reorg that re-includes a previously-
  claimed policy under a different parent block is the policy-
  validator's domain (`validators/policy.ak`) and is FUTURE WORK
  for R11 once the policy-validator symbolic executor lands
  (R9-T2 §10 item 7).
- **Concurrent batch txs**. Two concurrent BatchUnderwrite txs that
  both consume the same pool input are correctly rejected by
  Cardano's UTxO model at the consensus layer, not by the validator.
  The fuzz layer does not exercise this.

The MEV simulator + concurrency model is the **$10M-TVL milestone**
on the FV roadmap (see §7).

### S2. Plutus Core semantic bugs

The fuzz layer runs Aiken-emitted UPLC through the Plutus evaluator
inside `aiken check`. It DOES catch evaluator-level differences if
the encoder's arithmetic diverges from UPLC integer semantics
(e.g. division rounding). It does NOT catch:

- **`builtin` ambiguity**. If a future Plutus Core release changes
  the semantics of a `builtin` the validator depends on (e.g.
  `divideInteger` rounding mode), the property-fuzz layer in its
  current form does not flag the regression. IOG's CIP-117 conformance
  suite is the load-bearing source for this; Aegis tracks new
  Plutus-Core conformance suite drops as a separate workstream.
- **Script-cost-model drift**. The fuzz layer asserts correctness,
  not budget. A future cost-model change that pushes a validator
  branch over the per-tx execution budget would not surface here.
  The `D:/aegis/scripts/check_v12_2_deploy_constants.py` script is
  the load-bearing gate for cost-model pinning.

### S3. Cryptographic primitive composition

The fuzz layer treats `blake2b_256` and ed25519 as opaque builtins.
It does NOT exercise hash collisions on the NFT subject ID space,
signature malleability on the relay-presigned auth witness (v8;
see `project_aegis_v8_relay_presigned_auth`), or curve-point edge
cases. Cryptographic FV is deferred to R12+. The current crypto
surface is small and both primitives carry decades of scrutiny.

### S4. Off-chain bugs

The fuzz layer asserts on-chain validator correctness. It does NOT
exercise the PyCardano tx builders under `D:/aegis/offchain/`, the
CIP-30 wallet flow (`reference_cip30_sign_submit`), or the relay-
presigned witness construction. Off-chain FV is a separate
workstream (see `reference_aegis_v8_build_invariants`).

## 6. Reproducibility

### 6.1 Local — Windows + Git Bash

```bash
# Aiken layer (includes Team A's property tests)
cd D:/aegis/contracts
make fuzz-aiken    # invokes: cmd //c "aiken check 2>&1"

# Python differential fuzz layer
make fuzz-python   # invokes: pytest fuzz/ -v in symbolic_executor/

# Combined (CI baseline)
make fuzz-all

# Deep variant (nightly CI target; ~10-15 min wall time)
make fuzz-python-deep   # pytest fuzz/ -v --slow  (N=100000 per pair)
```

The `cmd //c` prefix on `aiken check` is the Windows-specific
workaround for Git Bash dropping aiken's stdout. See memory bank
`reference_aiken_windows_stdout_workaround`. On Linux CI the prefix
is a no-op (cmd /c just forwards the trailing command), so the same
Makefile rule runs unmodified across platforms.

### 6.2 Local — Linux / macOS

```bash
cd D:/aegis/contracts
make fuzz-all
```

The Makefile is platform-agnostic; the `cmd //c` workaround is
transparent on POSIX shells via Aiken's own stdout handling.

### 6.3 CI — GitHub Actions

The nightly workflow at `D:/aegis/.github/workflows/property-fuzz.yml`
runs on:

- `cron: "0 6 * * *"` (06:00 UTC nightly)
- `push` to `main` or `staging`
- `workflow_dispatch` (manual trigger from the Actions tab)

Each run executes:

1. `aiken-lang/setup-aiken@v1` pinned to `v1.1.22` (matches R8
   rebuild; see project memory
   `project_aegis_v12_validator_upgrade`).
2. Python 3.11 + `pytest`, `pytest-xdist`, `z3-solver`,
   `hypothesis`.
3. `make fuzz-aiken` (workflow inlines as `aiken check 2>&1 |
   tee aiken-fuzz.log` in the `contracts/` working dir).
4. `make fuzz-python` (workflow inlines as `pytest fuzz/ -v
   --junitxml=python-fuzz.xml`).
5. Artifact upload of `aiken-fuzz.log`, `python-fuzz.log`,
   `python-fuzz.xml` with 14-day retention.
6. If triggered by a PR, a summary comment is posted with the tail
   of both logs.

Artifact retention is intentionally short (14 days). The historical
record lives in this report and in the Round-10 README on the public
mirror.

### 6.4 CI — deep variant scheduling

The `--slow` deep variant runs as the nightly cron's primary
invocation. PR-triggered runs use the default N=1,000 to keep CI
turnaround under 5 minutes. The deep variant adds ~10-15 minutes per
nightly run.
