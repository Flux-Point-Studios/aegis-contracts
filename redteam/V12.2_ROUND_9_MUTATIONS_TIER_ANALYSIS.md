# V12.2 Round 9 — Mutation Survivor Tier Analysis

**Date**: 2026-05-19
**Companion to**: `V12.2_ROUND_9_MUTATIONS_POOL.md` (raw mutation output) and `V12.2_ROUND_9_SYNTHESIS.md` (Round-9 overview).
**Purpose**: Take the 248 surviving mutations in pool.ak and classify each cluster by ACTIONABILITY, then propose concrete regression tests that would kill the Tier-1 (security-relevant) survivors.

---

## Caveat on the 16 KILLED count

Eight of the 16 KILLED mutations are inside the R8 regression-test bodies (lines 1431-1446) — mutations on those lines flip the test's own assertions, which trivially makes the test fail. They are not "validator coverage" wins.

The remaining 8 KILLED mutations are inside aiken-side helper-function tests (`can_underwrite`, `calculate_fee_total`, etc.) where the helper itself is unit-tested. These ARE real coverage wins but they confirm what we already knew: aiken-side coverage is on helpers, not validator branches.

**Adjusted aiken-side validator-branch coverage**: effectively 0%. Validator branch coverage lives in pytest (596+ tests building real ScriptContexts via PyCardano) and live preprod txs.

---

## Three-tier classification

For each cluster of surviving mutations, classify by whether the mutated behavior would enable an ATTACK (Tier 1), be caught by a redundant guard (Tier 2), or break the protocol without enabling exploitation (Tier 3).

### Tier 1 — Security-relevant test gaps (backfill recommended before audit)

These are surviving mutations on lines whose mutated behavior would let an INVALID transaction be accepted by the validator (i.e., the validator becomes weaker). 0% aiken-side coverage on these clusters; only pytest integration tests catch them today.

#### Cluster T1-A: Final `&&`-chain accept clauses (35 survivors)

| Line | Branch | Survivors |
|---|---|---|
| 791  | Underwrite (`coverage_positive && premium_positive && ... && partner_output_funded`) | 12 |
| 1136 | BatchUnderwrite (`coverage_positive && ... && partner_outputs_funded && donation_ok`) | 12 |
| 1387 | AcceptCancellation (`policy_targets_this_pool && bounds_ok && ... && partner_output_funded`) | 11 |

**Why Tier 1**: each chain has 12-13 boolean guards `&&`'d together. A mutation `&&` → `||` collapses the chain so ANY single True is sufficient — the validator accepts a tx that fails most of its safety checks (e.g., the pool-NFT not present, the policy datum mismatching, the donation underfunded). An attacker can construct a tx that passes one guard and weaponizes the bypass.

**Recommended Tier-1 regression tests** (aiken-side, one per branch — each test asserts validator REJECTS when exactly one guard is False):

```aiken
test underwrite_rejects_when_coverage_not_positive() {
  // Build a synthetic ScriptContext where coverage_amount == 0; assert spend(datum, redeemer, ctx) == False.
}
test underwrite_rejects_when_donation_underfunded() {
  // Build ScriptContext with treasury_donation < required; assert validator rejects.
}
test underwrite_rejects_when_partner_output_missing() {
  // Build ScriptContext with partner_address=Some(addr) but no output to addr; assert rejection.
}
// ... 4-5 similar tests per branch, one per critical guard.
```

Total: ~12-15 new aiken-side ScriptContext tests across the three branches. Each test ~30-60 lines (datum + redeemer + tx synthesis + assertion). Effort: ~1.5 days for one engineer.

#### Cluster T1-B: Immutable pool-datum equality chains (35 survivors)

| Line | Branch | What it protects |
|---|---|---|
| 452  | Underwrite policy-datum check | `pdat.pool_script_hash == own_pool_hash && pdat.pool_nft == own_pool_nft && pdat.coverage_amount == coverage && pdat.premium_paid == premium` (9 survivors) |
| 677  | Underwrite pool-datum immutability | `new_datum.lp_token_policy == datum.lp_token_policy && new_datum.protocol_fee_bps == datum.protocol_fee_bps && new_datum.pool_nft == datum.pool_nft && new_datum.lp_supply == datum.lp_supply` (7 survivors) |
| 857  | ProcessClaim pool-datum immutability (same shape) | 7 survivors |
| 1025 | AddLiquidity pool-datum immutability (same shape) | 7 survivors |
| 1184 | BatchUnderwrite pool-datum immutability (same shape) | 7 survivors |
| 1329 | AcceptCancellation pool-datum immutability (same shape) | 7 survivors |

**Why Tier 1**: these chains prevent pool-state tampering across the validator's transitions. Mutating `==` → `!=` on the lp_token_policy / pool_nft / protocol_fee_bps fields lets an attacker construct a continuing pool output with a DIFFERENT lp_token_policy or pool_nft (effectively forking the pool's identity). The exploit shape: claim against pool A's NFT but produce a continuing output bound to pool B's NFT, drain pool A.

**Recommended Tier-1 regression tests**:

```aiken
test underwrite_rejects_mutated_lp_token_policy() {
  // Build ScriptContext where the continuing pool output's new_datum.lp_token_policy
  // differs from datum.lp_token_policy by one byte. Assert spend rejects.
}
test process_claim_rejects_mutated_pool_nft() {
  // Same shape for ProcessClaim branch.
}
test add_liquidity_rejects_mutated_protocol_fee_bps() {
  // Test that the validator does not allow protocol_fee_bps to drift across AddLiquidity.
}
// ... one test per immutable field per branch (6 fields × 5 branches = 30 tests, but most can be parameterized).
```

Parameterize via aiken's test helpers if available to reduce 30 → ~10 tests. Effort: ~1 day.

#### Cluster T1-D: AcceptCancellation refund invariants (11 survivors)

| Line | Check | Survivors |
|---|---|---|
| 1310 | `refund_amount >= 0 && refund_amount <= datum.total_liquidity && policy_datum.coverage_amount <= datum.active_coverage` | 5 |
| 1324 | `new_datum.total_liquidity == datum.total_liquidity - refund_amount - fee_total_cancel && new_datum.active_coverage == ...` | 3 |
| 1333 | `new_datum.total_liquidity >= 0 && new_datum.active_coverage >= 0` | 3 |

**Why Tier 1**: AcceptCancellation arithmetic invariants. Mutations here let refund_amount drift (e.g., `<=` → `<` on the upper bound makes the validator ACCEPT refund_amount == datum.total_liquidity, which it shouldn't because that would leave the pool insolvent for in-flight policies).

**Recommended Tier-1 regression tests**:

```aiken
test accept_cancel_rejects_refund_above_total_liquidity() {
  // ScriptContext where the consumed policy claims refund_amount > datum.total_liquidity; assert rejection.
}
test accept_cancel_enforces_total_liquidity_arithmetic() {
  // Test that new_datum.total_liquidity == datum.total_liquidity - refund_amount - fee_total_cancel exactly,
  // by constructing a continuing output that's off by 1 lovelace and asserting rejection.
}
test accept_cancel_rejects_negative_active_coverage_continuation() {
  // The "wait this could go negative" guard at line 1333.
}
```

Effort: ~half day for ~5 tests.

**Tier-1 total backfill estimate**: ~4 days for ~50 aiken-side ScriptContext regression tests covering the four clusters above. After backfill, expected mutation kill rate on these lines: 90%+.

### Tier 2 — Defense-in-depth (redundant guard catches; lower priority)

Surviving mutations on lines where another guard in the same branch catches the bad case. Backfilling these is not security-critical (the attack is blocked by the redundant guard) but does tighten the test signal.

| Line | Why Tier 2 |
|---|---|
| 1114 | Inside `partner_address_not_aliased` helper body. The helper IS exercised by the 5 new R8 regression tests at lines 1431-1446 (KILLED) — but individual `&&` clauses in the helper body have multiple paths and only one is tested per regression. Mutating internal clauses survives because the union of test inputs doesn't probe every clause. Acceptable for now: the helper's *contract* is tested. |
| 305  | `pdat.partner_share_bps >= 0 && pdat.partner_share_bps <= partner_share_cap_bps` — partner-bound check at policy creation. R8's `partner_consistency` check at the validator level enforces the same bound; flipping this helper's check is caught upstream. |
| 1281 | Same partner-bound check on the AcceptCancellation path. Same redundancy. |
| 518  | `output_to_address_at_least` body — generic helper called with specific (addr, required_lovelace) pairs by team_output_funded / partner_output_funded. The MUTATION on `>=` to `>` would let outputs with exactly required_lovelace fail; but the callers' downstream `team_output_funded && partner_output_funded` then fails, so the validator still rejects. |
| 600  | Pool continuation output match: `output.address == own_address && output_has_nft(...)`. Mutating one term lets the validator accept outputs at different addresses OR without the NFT — but the SUBSEQUENT NFT-presence + pool_datum-decode guards catch the bad case at line 670+. Defense-in-depth. |

**Tier 2 backfill effort**: lower priority. If we have spare cycles, add ~5 tests targeting each helper's input boundaries.

### Tier 3 — Spec-equivalence or harmless

Mutations where the mutated behavior breaks the protocol (validator rejects valid txs) but does not enable an attack. The validator becomes STRICTER, not WEAKER.

| Line | Why Tier 3 |
|---|---|
| 65, 69, 84 | `consumed_policies_total_to` helper. Mutating `==` → `!=` makes the helper sum from inputs at OTHER scripts (or compare to wrong expected_total). Result: helper returns False on valid txs, validator rejects. No attack surface — protocol becomes uncallable, not exploitable. |
| 231 | `cov_sum == total_coverage && prem_sum == total_premium && funded_ok`. Same shape — if the equality is flipped, the batch walker rejects valid sums. Strict-failure, not exploit. |
| 377 | `funded_ok: totals.funded_ok && totals.cov_sum == total_coverage && totals.prem_sum == total_premium` — batch totals record assignment. Mutating the equality embeds wrong totals into the record; downstream check at line 1037 (`batch_policies_funded`) then fails. Strict-failure path. |
| 1150 | `let returned_positive = total_returned > 0`. Mutating `>` to `>=` lets returned == 0 pass the gate; but the downstream check at line 1193 (`new_datum.total_liquidity >= 0 ...`) catches it; AND the helper itself is upstream-bounded by the consumed-policies sum. Defense-in-depth + spec-equivalence in normal operation. |
| 209, 300 | `if pdat.pool_script_hash == own_pool_hash && pdat.pool_nft == own_pool_nft && time_ok && ...` — these are the per-policy match gates in the BatchUnderwrite walker. If we flip the equality, no policies match and the walker returns zero. Validator then rejects the batch because aggregated sums don't reach total_coverage / total_premium. Spec-equivalence: stricter than intended, doesn't enable attack. |

**Tier 3 backfill**: not recommended. These mutations represent "the protocol still safe, just broken" states. Worth a small note in the spec doc, not test backfill.
